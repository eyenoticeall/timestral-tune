# AGENTS.md

Guide for anyone, human or coding agent, picking up work in this repository.

## 1. Orientation

`timestral-tune` is an adaptation toolkit (fine-tuning, LoRA, conformal calibration) for Mistral's
Timestral time-series models. It is **alpha** (v0.1): Phases 0–4 (rescoped: replay/distillation and
Apple GPU 123M/209M/long-context coverage) and Phase 5 Stages 1–2 (experimental single-node multi-process
training including replay/distillation, verified on CPU/`gloo` on macOS arm64 and Linux x86_64, exercised on
one NVIDIA L4 with shared-GPU NCCL, and exercised in a separate-GPU PCIe/SHM Stage 3 session on 4× NVIDIA
GeForce RTX 3060; remaining Stage 3 items — T15 on NCCL, NVLink/P2P, tier calibration, and scaling — open)
are built; tiled DHF training is deferred as exploratory.

Read in this order before changing anything:

1. `docs/STATUS.md` — where the project is right now and what is next.
2. `docs/SPEC.md` — the specification and overview guide. It is the source of truth
   for design. Sections: §3 model facts, §4 loss, §5 modes, §6 architecture, §7 API, §9 acceptance tests,
   §10 roadmap, §11 decisions, §12 open questions.
3. The last entry of `docs/DEVLOG.md` — what the previous session did and left open.
4. The notes file for the current phase in `docs/phases/`.

Reference when needed: `docs/DEVELOPMENT.md` (setup, commands, testing), `docs/UPSTREAM.md` (vendored
code), `docs/VERIFICATION.md` (measured evidence).

## 3. Rules

1. **Tag provenance.** Every technical claim in the spec carries a tag: `[P §x]` paper, `[U file:line]`
   official code at the pinned commit, `[H]` Hub config, `[V]` verified by running a checkpoint, `[D]` our
   design. Keep doing this. A new `[V]` claim needs a probe in `scripts/probes/` and a row in
   `docs/VERIFICATION.md`. Do not state as fact what you have not checked.
2. **The spec and the code must agree.** If implementation shows the spec is wrong, fix the spec in the
   same change and say why in the devlog. Do not silently diverge.
3. **Never hand-edit `src/timestral_tune/_vendor/`.** It is generated by `scripts/vendor_upstream.py`.
   New logic goes outside it (subclass or wrap). A test fails if a vendored file changes.
4. **Acceptance tests define done.** A feature is done when its tests from spec §9 pass. A skipped
   placeholder is not a pass. Keep the test names (`test_tNN_*`).
5. **No weights or Hub files in the repo.** No `*.safetensors`, no checkpoint `config.json`, no trained
   outputs. They fall under Mistral's weights licence.
6. **No private or machine-specific details** in tracked files: no usernames, home paths, email
   addresses or local paths to other projects.
7. **Reference PDFs:** only papers with a licence that allows redistribution are tracked (`papers/README.md`).
8. **Tick a roadmap box only for work that ran and passed.** If it was written but not exercised, say so.

## 4. Commands

```bash
uv sync                                   # environment (Python 3.10+)
uv run pytest                             # all tests; acceptance placeholders report as skipped
uv run pytest -m "not network"            # what CI runs
uv run ruff check . && uv run ruff format --check .
uv run ruff format .                      # apply formatting
uv build                                  # wheel and sdist into dist/
python scripts/check_upstream_drift.py    # has upstream moved since we vendored?
uv run python scripts/probes/<name>.py    # verification probes (download checkpoints on first use)
```

## 5. Session workflow

**Start:** read the files in §1. Confirm `uv run pytest` and lint are green before you begin.

**During:** work on `main` unless the work qualifies for a branch (§6). Implement against the spec section and acceptance tests named in the
stub's docstring. Commit in small logical steps.

**End, every session, even if unfinished:**

1. Update `docs/STATUS.md`: state, what is verified, what is next, known issues.
2. Append a dated entry to `docs/DEVLOG.md`: what was done, decisions, evidence, what is open.
3. Update the phase notes file with anything a successor needs.
4. Tick spec §10 boxes for work that ran and passed; add or change §11 and §12 if decisions or risks changed.
5. Commit those documentation updates.

## 6. Commits and branches

- **Work on `main` by default.** Fixes, documentation, tooling and other small or self-contained changes
  are committed straight to `main`.
- **Branches are reserved** for three things: a roadmap phase (`phase-1`), a new version (`v0.2`), or a
  large adaptation that will take many commits and may not land (`adapt/tiled-training`). One branch per
  such effort, not one per task within it. Keep the number of open branches small.
- **The maintainer can ask for any other branch.** A branch outside those three, including one stacked on
  another branch (a `fix/...` branch on top of `phase-1`), is fine when the maintainer requests it. Do not
  open one on your own initiative, and do not flag one the maintainer asked for as a policy problem.
- **Close branches out.** When a branch's work is merged, fast-forward `main` where possible and delete the
  branch. Do not leave merged branches around.
- **One logical change per commit.** Do not mix a feature with unrelated formatting or docs. Tests for a
  change go in the same commit as the change.
- **Every commit should pass** `uv run pytest -m "not network"` and lint, so history stays bisectable.
- **Conventional Commits** format: `type(scope): summary` in the imperative, at most about 72 characters.
  - Types: `feat`, `fix`, `test`, `docs`, `build`, `ci`, `refactor`, `perf`, `chore`.
  - Scopes: `vendor`, `data`, `models`, `lora`, `conformal`, `losses`, `trainer`, `export`, `replay`,
    `lacuna`, `probes`, `spec`.
- **Body:** say why, not just what. Name the spec section and acceptance tests the commit addresses, and
  any evidence (for example "T1, T2 pass on 5M and 28M").
- **Documentation updates** from §5 go in their own `docs:` commit at the end of the session, unless a
  spec change is inseparable from the code change it describes.
- **Re-vendoring** is always its own commit: `build(vendor): re-vendor timestral at <short sha>`.
- **Do not push, merge a branch into `main`, tag or publish** unless the maintainer asks.
