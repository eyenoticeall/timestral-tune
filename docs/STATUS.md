## Open questions and known issues

Full list in spec §12. The ones that matter next:

- **CUDA and CPU `torch.compile` need a C++ compiler and Python headers** with recent PyTorch (spec §12). Ubuntu's system Python lacks `Python.h` without `python3-dev`; use a `uv`-managed Python. `scripts/cuda_check.sh` checks for them.
- **Phase 5 Stage 3 remains open overall** despite the passing 4× RTX 3060 PCIe/SHM separate-GPU session S6 (`3ac7c6d`, `docs/VERIFICATION.md` §17.4): T15 on NCCL, NVLink / GPU P2P transport and cross-GPU run-to-run determinism, `bf16`/released-weights tier calibration, and 1/2/4-GPU scaling/VRAM measurements remain open.
- **NCCL rank death aborts survivors via `SIGABRT` without Python cleanup** (`docs/VERIFICATION.md` §17.4, spec D35/§12): in both single-L4 shared-GPU checks (`8e8f490`, `d474f82`) and separate-GPU 4× RTX 3060 PCIe/SHM checks (`3ac7c6d`), surviving NCCL ranks were killed by `SIGABRT` after the process-group timeout plus NCCL's health-check wait with no Python exception raised, so `except`/`finally` blocks inside `fit()` and user scripts did not run. By contrast, CPU/`gloo` raised Python `RuntimeError` (promptly on TCP transport reset on Linux, or at the process-group timeout on macOS arm64), allowing `finally` cleanup.
- **Compiled CUDA rows vary run-to-run** (`docs/VERIFICATION.md` §17.4, spec §12): `compile_default_lora_variate` and `compile_default_lora_replay` differed across repeated L4 sessions (including across S3–S5 on the same machine type and GPU driver, per the provisioning records), while non-compiled CUDA rows matched in their printed parity columns and `vram_mib` (timing columns varied); cause uninvestigated (S6 ran once on 4× RTX 3060, so separate-GPU run-to-run variation is unmeasured).
- **`load_model(..., dtype=torch.float64)` truncates weights to float32 before casting** (spec §12 observation #12, `docs/VERIFICATION.md` §11): `load_model` constructs `TuneTimestralModel(config)` in default float32, loads weights into it, and casts afterward, so a `float64` export cannot be reloaded to better than float32 precision. Recorded, not changed.
- **macOS `TMPDIR` length silently deadlocks `DataLoader` workers (`num_workers > 0`)** (spec §12, `docs/DEVELOPMENT.md`): a `TMPDIR` of ~70 bytes overflows macOS's 103-byte `AF_UNIX` `sun_path` limit in `torch_shm_manager`, leaving workers alive at 0% CPU while one-process or multi-process `fit()` hangs forever; run with `TMPDIR=/tmp` (`scripts/multi_gpu_check.py` enforces this automatically).
- **PyTorch `F.linear` `requires_grad` dispatch on non-contiguous inputs** (spec §12, `docs/VERIFICATION.md` §17.2): causes step-0 round-off differences between student and identical-weight frozen teacher in `full_ft` distillation on CPU (measured on macOS arm64 and three Linux x86_64 VMs, where standalone `float64` is non-zero too and magnitudes/shapes vary across x86_64 CPUs; left unchanged pending maintainer decision).
- **PyTorch 2.4.0 on macOS hangs at exit when a DataLoader uses worker processes.** Gone by 2.8.0 (`docs/VERIFICATION.md` §10). `num_workers` defaults to 0.
- **`compile_model=True` on PyTorch 2.4.0 with Python older than 3.12 needs `setuptools` installed.** That PyTorch wheel does not declare it (`docs/VERIFICATION.md` §10).
- **CI actions use a deprecated Node.js version.** GitHub warns that `actions/checkout@v4` and `astral-sh/setup-uv@v5` target Node.js 20. They still run.
