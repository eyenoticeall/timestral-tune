## 1. Executive Summary & Vision

`timestral-tune` is an open-source, pure-PyTorch adaptation toolkit for Mistral AI's **Timestral** time-series foundation models (`Timestral-5M`, `28M`, `123M`, `209M`).

The official `mistralai/timestral` repository provides inference only (`TimestralForecaster`). Mistral's announcement offers fine-tuning, training-mix control and replay of pre-training data through its commercial Forge product, and publishes no training code. `timestral-tune` fills that gap for the open weights.

The library prioritises **anti-forgetting adaptation**. It offers a ladder of increasing intervention: post-hoc conformal calibration, head probing, selective low-rank adaptation (LoRA), full fine-tuning, and replay mixing. No custom C++ or CUDA build steps are needed.

### What "faithful to the paper" does and does not mean

The paper specifies the objective, the attention masks, the normalisation, and the architecture. This library reproduces those exactly and tests the reproduction against the released code and weights.

The paper does **not** specify an optimiser, learning rate, schedule, batch size, block-length distribution, or augmentation settings, and Mistral has not released its synthetic corpus. Everything in those areas is our design **[D]** and is validated empirically in Phase 3.

### Non-goals for v0.1

- Reproducing Mistral's pretraining or post-training.
- Architectural extensions (new covariate types, new heads).
- Training horizons longer than one decode block (1,024 steps) in a single forward pass.
- Re-hosting or redistributing Mistral's weights.

### Key Technical Pillars

1. **Faithful Decoupled Horizon Forecasting (DHF).** Context patches and forecast positions use separate tokens. Context is encoded causally and is never masked to create a horizon; prediction tokens read the context and never write to it **[P §3.1]**. The library reuses the upstream mask builders unchanged and proves its training forward pass equal to upstream inference.
2. **Role-aware pinball loss in normalised space.** The 21-quantile pinball loss is computed in the model's normalised space and only on observed target values in the forecast horizon. Past-only and known-future covariates are inputs and are never scored **[P §4.1, §3.2]**.
3. **Anti-forgetting adaptation ladder.** Five modes of increasing capacity, plus replay mixing and a forgetting metric, so that small domain datasets do not destroy the pretrained priors.
4. **Auditable outputs.** Every run records its parameters, data fingerprint and metrics. An optional integration writes trial records and signal frames in the form Lacuna consumes, so Lacuna can apply its multiple-testing and overfitting checks.

## 3. Model Facts the Design Depends On

### 3.1 Architecture

| | 5M | 28M | 123M | 209M |
|---|---|---|---|---|
| `d_model` | 192 | 384 | 640 | 768 |
| Blocks | 8 | 12 | 20 | 24 |
| Heads (head dim 64) | 3 | 6 | 10 | 12 |
| SwiGLU width | 512 | 1024 | 1712 | 2048 |
| Temporal-attention modules | 8 | 12 | 20 | 24 |
| Variate-attention modules | 2 | 3 | 5 | 6 |
| Layers holding variate attention | 3, 7 | 3, 7, 11 | 3, 7, …, 19 | 3, 7, …, 23 |
| Parameters | 5.2M | 27.8M | 122.6M | 209.3M |

Sources: **[P Table 1]**, **[H]**. All four checkpoints share `patch_size=32`, `block_size=32`, `context_length=32768`, and `quantile_width_factor=3.0` **[H]**.

- **Other sizes.** The library does not depend on these four sizes. Every dimension in the table, and the patch size, block size and context length, is read from the checkpoint's `config.json` **[U config.py:42-49]**; the four size names appear in our code only as pinned Hub revisions **[D]**. A checkpoint of another size is supported when it keeps the released architecture: layer kinds `time` and `time_variate`, the `sdpa_sigmoid` gate, and the 21 quantile knots **[H]**. Unknown config keys and unknown or missing parameters are load errors **[U config.py:120-123]**. The vendored config also accepts the layer kinds `variate` and `variate_time`, the `none` gate and other quantile knots **[U config.py:14-15, 70-76]**; such a checkpoint loads, but no released model uses them and no test here trains them. Tested network-free: one non-released shape goes from a local directory through the trainer in all four modes to an export the upstream loader accepts, and the suite's tiny model, a second non-released shape, covers the same steps separately (`docs/VERIFICATION.md` §8). Nothing above 209M has been run, and the default learning rates were swept on 5M to 209M only.
- **Patching.** Each patch is 32 time steps, embedded from its normalised values plus per-step missing indicators **[P §3.3]**.
- **Limits.** Context up to 32,768 steps (1,024 patches). One decode block covers up to 32 patches (1,024 steps); longer horizons are decoded block by block, feeding medians back **[P §3.1]**.
- **Blocks.** Pre-norm, RMSNorm, SwiGLU. Every block has temporal attention; every fourth block also has variate attention. Both use a sigmoid output gate. No dropout or stochastic depth was used **[P §3.3]**.
- **Head.** A two-layer residual MLP emits 21 non-crossing quantiles per time step. The median is free; other levels are cumulative softplus increments **[P §3.3]**, **[U model.py:57-76]**.
- **Read the checkpoint config.** `quantile_width_factor` is 3.0 in every released checkpoint but defaults to 2.0 in the code **[H]**, **[U config.py:63]**. Never construct a config from code defaults.

### 3.2 Module naming, which dictates the LoRA design

- Attention modules live at `transformer.layers.{i}.attns.{j}`. Temporal and variate attention are the same class, told apart only by the `is_time` attribute **[U layers.py:143-159]**. No module is named `variate_attn`, `q_proj` or `v_proj` **[V]**.
- Each attention module has three bias-free linears: `wQKV` (`d_model → 3·d_model`, fused), `wO`, and `_gate` **[U layers.py:157-159]**, **[V]**.
- In `wQKV.weight`, rows `[0, D)` are the query projection, `[D, 2D)` the key projection, and `[2D, 3D)` the value projection, where `D = d_model` **[U layers.py:161-166]**. The run confirmed that the last third is the value projection and the first two-thirds are query and key together **[V]**; the order of query and key within those two-thirds is from the code only.
- The head is `head.projection`, three bias-free linears **[U model.py:87-89]**. Its size is `4D² + 3360·D` parameters: 792,576 for 5M, which is 15.2% of the model **[V]**. The same formula gives about 6.8% for 28M, 3.1% for 123M and 2.4% for 209M.

### 3.3 Roles, masks and normalisation

Each row is a target, a past-only covariate or a known-future covariate. Roles are not embedded; they act only through masks and the choice of normalisation **[P §3.2]**.

| | Temporal attention | Variate attention | Normalisation |
|---|---|---|---|
| Target | causal | reads targets and both covariate kinds | causal per patch, then asinh |
| Past-only covariate | causal | reads past-only and known-future covariates; never targets | causal per patch, then asinh |
| Known-future covariate | whole window | reads known-future covariates only | whole-window statistics; 0/1 indicator rows left unchanged |

Sources: **[P §3.2, §3.3]**, **[U masks.py:104-118]**, **[U model.py:135-151]**.

Verified on the 5M checkpoint **[V]**: noise added to a target's context changed neither covariate row's output (0.00); noise on a past-only covariate changed the target and itself but not the known-future row; noise on a known-future covariate changed all three.

### 3.4 Two inference layouts

Upstream uses two token layouts, and training mirrors both.

- **No covariates** **[U model.py:204-229]**: `L` context tokens followed by `h` prediction tokens. Masks come from `build_forecast_time_mask` **[U masks.py:34-47]**.
- **With covariates** **[U model.py:231-273]**: upstream uses a window of `n = L + h` patches with `n` encoder tokens and `n` prediction tokens (`2n` in total); target and past-only rows hold a blank, unobserved horizon while known-future rows hold their real future values, and only the `h` horizon prediction tokens are read out. In single-horizon training, the leading `L` prediction tokens are inactive (they attend only to themselves and are never read by any other token), so `training_forward` drops them and runs `L + 2h` tokens (`n` encoder tokens plus `h` active horizon prediction tokens) **[D]** (decision D16). Masks come from `_build_covariate_time_mask` (built from upstream's `enc_causal_mask`) and `build_two_stream_variate_mask` **[U masks.py:121-146]**, verified bit-identical to slicing upstream's `build_two_stream_time_mask` **[U masks.py:68-101]**.

### 3.5 What upstream does not expose

- `predict_block` returns raw-space quantiles after `sinh` denormalisation **[U model.py:229, 273]**. The normalised head output needed for the loss is only reachable through the private `_run_two_stream` **[U model.py:153-162]**.
- `TimestralForecaster.forecast` runs under `torch.inference_mode()` **[U forecaster.py:160]**, so it cannot be used for training.
- Statistics are computed in float64, which the Apple GPU backend does not support **[V]**. There are four such sites: the causal statistics **[U scaler.py:29]** (reached from `model.scale` and from the forecaster's `_cap_quantiles`), `advancing_block_frames` **[U scaler.py:185]**, `_refine_block` **[U forecaster.py:472]**, and `_encode_categorical` **[U forecaster.py:265]**. §5.4 describes the workaround.
- `TimestralConfig.from_dict` rejects unknown keys **[U config.py:121-124]**, so no extra metadata may be written into `config.json`.

## 4. Mathematical & Loss Mechanics

### 4.1 Quantile levels and pinball loss

The model predicts 21 non-crossing quantiles **[P §4.1]**:

$$\mathcal{Q} = \{0.01, 0.05, 0.10, 0.15, \dots, 0.85, 0.90, 0.95, 0.99\}$$

For a normalised target $z$ and predicted quantile $\hat{q}_\tau$ at level $\tau \in \mathcal{Q}$ **[P eq. 2]**:

$$\rho_\tau(e) = \max\big(\tau e,\ (\tau - 1)e\big), \qquad e = z - \hat{q}_\tau$$

### 4.2 Scored positions and batch loss

Let $i$ index (row, horizon time step) pairs in a batch, and let $w_i \in \{0, 1\}$ with $w_i = 1$ if and only if all of the following hold:

- the row is a **target** (not a covariate);
- the step lies in the **requested forecast horizon** (not in the padding that rounds the horizon up to a whole patch);
- the value is **observed**.

The loss averages equally over quantile levels and scored positions **[P eq. 3]**:

$$\mathcal{L} = \frac{1}{|\mathcal{Q}| \sum_i w_i} \sum_i w_i \sum_{\tau \in \mathcal{Q}} \rho_\tau\big(z_i - \hat{q}_{\tau, i}\big)$$

A batch with $\sum_i w_i = 0$ is skipped rather than divided by an epsilon **[D]**. Context representations and covariates receive no direct loss; they are trained through their influence on scored predictions **[P §4.1]**.

### 4.3 Normalised space

Targets and predictions are compared in the model's normalised space **[P §4.1]**. For a step in horizon patch $j$ of a block (with $j = 0$ the first):

$$z = \operatorname{asinh}\!\left(\frac{y - \mu_j}{\sigma_j}\right)$$

Because this map is increasing for a fixed frame $(\mu_j, \sigma_j)$, quantiles of $z$ map one-to-one onto quantiles of $y$. Raw-space forecasts are $\sinh(\hat{q}) \cdot \sigma_j + \mu_j$.

**The frame $(\mu_j, \sigma_j)$:**

- **First patch ($j = 0$).** Mean and standard deviation of all observed context values up to the end of the last context patch **[P §3.3]**, **[U model.py:227-228]**. Settled.
- **Later patches ($j \ge 1$).** The paper standardises each forecast patch with all values up to the end of the preceding patch. Inside a block those include earlier forecast patches, "which are unknown at inference and are therefore replaced by their predicted medians. The same statistics are used during training to standardise the targets, so that training and inference match" **[P §3.3]**.

We read that as: training folds the model's own predicted medians into the statistics. The upstream forecaster always denormalises later patches this way, in `_refine_block` and `advancing_block_frames` **[U forecaster.py:458-483]**, **[U scaler.py:165-208]**.

**Decision [D]:** train in the **median-folded frame** with stop-gradient on the statistics, reusing `advancing_block_frames` unchanged. Whatever pretraining did, this makes the tuned model's training frame identical to its deployment frame.

**Evidence [V].** The released checkpoints are calibrated in this frame. On synthetic series with short contexts and a 16-patch horizon, the 5M and 28M models' 80% interval covers 76–85% of targets normalised in the median-folded frame on horizon patches 1–15, against 88–100% of targets normalised in the true-values frame. Patch 0, which is identical under both frames, sits at 80–83%. A model trained against true-values targets would be calibrated under that frame instead of over-covering, so pretraining is consistent with the median-folded frame and not with the other. This supports the reading above by measurement, not only by the paper's wording.

Limits of that evidence: synthetic, univariate, fully observed series; one seed; two model sizes. Under the median-folded frame the 50% interval under-covers at long lead times (0.40–0.44 on patches 4–15). Numbers and the probe are in `docs/VERIFICATION.md`.

An alternative frame, `true_values` (statistics from the true series up to the preceding patch), is available as `target_frame="true_values"` for ablation. Pinball losses are not comparable between the two frames: each is measured in its own normalised units, and true-values frames have larger scales on drifting series, so they score lower whatever the model predicts.

Reported metrics (§5.5) are always computed in raw space.

## 5. Adaptation Modes

| Mode | Trainable parameters | Primary use case | Overfitting risk |
|---|---|---|---|
| `conformal` | None by gradient; a small table of offsets is fitted | Low-data regimes, real-time risk buffers | Very low |
| `head_only` | `head.projection` only (15.2% of 5M, about 2.4% of 209M) | Distribution-shape shifts, e.g. financial return tails | Low; moderate on 5M, where the head is a large share |
| `lora_variate` | LoRA on variate attention, `r = 4..16` | Cross-series dependency changes while temporal priors stay frozen | Low to moderate |
| `lora_temporal` | LoRA on temporal attention, `r = 4..16` | Seasonality and regime adaptation | Moderate |
| `full_ft` | All weights | Large datasets (1,000+ series) | High; lower LR or pair with distillation / real-data replay (§5.3) |

Modes are presets over one mechanism: a set of trainable parameter groups plus optional LoRA wrappers **[D]**.

### 5.1 LoRA design

Because query, key and value share one fused `wQKV` linear (§3.2), name-based injection through a generic library cannot target Q and V separately. The library ships a small custom adapter **[D]**.

- **Slices.** `LoraConfig.targets` selects from `"q"`, `"k"`, `"v"` (row slices of `wQKV`), `"o"` (`wO`) and `"gate"` (`_gate`). `LoraConfig.axes` selects `"time"`, `"variate"`, or both, by reading each module's `is_time`.
- **Update.** For each selected slice, $\Delta W = \frac{\alpha}{r} B A$ with $A \in \mathbb{R}^{r \times D}$ Gaussian-initialised and $B \in \mathbb{R}^{D \times r}$ zero-initialised, so the adapted model equals the base model at step 0 (LoRA paper, eq. 3 and §4.1).
- **Size.** Trainable parameters are `modules × slices × 2·r·D`. For 28M with `r=8` on Q and V: 36,864 for `lora_variate` (3 modules) and 147,456 for `lora_temporal` (12 modules).
- **Merge.** `merge()` adds $\Delta W$ into the slice rows in place; export writes merged weights under upstream parameter names (§7.4).

**Single-row guard.** Variate attention attends across the rows of one series. When a series has a single row, there is one key, the softmax is identically 1, and the query and key projections have no effect on the output. Verified: perturbing them on a univariate input changed the forecast by exactly 0, while perturbing the value projection changed it **[V]**. Therefore:

- `lora_variate` raises a configuration error if every series in the dataset has exactly one row and no covariates.
- It can be overridden with `allow_single_row=True`, in which case only `"v"`, `"o"` and `"gate"` are permitted, and the docs state that this is a per-token transform, not a cross-series one.

### 5.2 Conformal calibration

Conformal calibration adjusts the final forecast quantiles after all inference steps (including the forecaster's symmetric averaging and clipping). It never touches model weights.

**Level pairs.** The 21 levels form ten symmetric pairs $(\tau, 1 - \tau)$ around the median, giving nominal central coverages of 98%, 90%, 80%, 70%, …, 10%. A requested coverage must be one of these; the calibrator raises otherwise.

**Static method: Conformalized Quantile Regression** (`fit` / `transform`). For a pair with miscoverage $\alpha = 2\tau$ and a calibration set of size $n$:

$$E_i = \max\big(\hat{q}_{\tau}(x_i) - y_i,\ \ y_i - \hat{q}_{1-\tau}(x_i)\big)$$

$$Q = \text{the } (1 - \alpha)(1 + 1/n)\text{-th empirical quantile of } \{E_i\}$$

$$C(x) = \big[\hat{q}_{\tau}(x) - Q,\ \ \hat{q}_{1-\tau}(x) + Q\big]$$

(CQR paper, eqs. 9–11.) $Q$ is the exact finite-sample order statistic $\lceil (n + 1)(1 - \alpha) \rceil$ (taking $\max_i E_i$ when the rank exceeds $n$) and may be negative, which narrows an over-wide interval.

Design choices **[D]**:

- **Horizon buckets.** Forecast error grows with lead time, so offsets are fitted per horizon bucket (default: one per patch of 32 steps; configurable down to one per step).
- **Score scaling.** Scores are divided by the context standard deviation of each series before pooling, and multiplied back at transform time, so that series with different scales share one calibration set.
- **Monotonicity repair.** Independent offsets per pair can break nesting or cross the median. The median is never shifted. Calibrated levels are clamped so they do not cross the median and repaired outward relative to each other (so calibrated pairs can only widen against other calibrated pairs); uncalibrated levels are then reconciled into the bounds between adjacent fixed anchors (or outward beyond the outermost anchor) without moving any calibrated level. When all ten pairs are calibrated (`target_coverage="all"`), this reduces identically to pure outward repair; when a single pair such as `0.80` is calibrated, negative offsets still narrow that pair cleanly instead of being pulled back outward by uncalibrated neighbours.
- **Calibration data.** Must be disjoint from training data and later in time than it. `collect_conformal_data(forecaster, dataset)` produces `(predictions, actuals, context_scale)` from a `TimeSeriesDataset` through upstream `TimestralForecaster.forecast()`.

**Online method: Adaptive Conformal Inference** (`update` / `transform`). The working miscoverage level is adjusted after each realised observation:

$$\alpha_{t+1} = \alpha_t + \gamma\,(\alpha - \mathrm{err}_t), \qquad \mathrm{err}_t = \mathbb{1}\{y_t \notin C_t(\alpha_t)\}$$

(ACI paper, eq. 2.) The offset at time $t$ is the $(1 - \alpha_t)$ quantile of a rolling window of the last `window` forecast observations per bucket (default 500 forecasts; serialised `conformal.json` is ~1 MB for one pair or ~10 MB for `"all"` at horizon 96), and $\mathrm{err}_t$ is evaluated against the actual emitted (anchor-repaired) interval. For multi-step forecasts, each horizon bucket keeps its own $\alpha_t$ and updates when its observation arrives; when `bucket_size > 1`, $\mathrm{err}_t \in [0, 1]$ is the mean miscoverage fraction over observed steps in the bucket (**[D]** batch-ACI).

The recursion can push $\alpha_t$ slightly outside $[0, 1]$; the ACI paper proves it stays in $[-\gamma, 1 + \gamma]$ (Lemma 4.1) because the paper emits $(-\infty, +\infty)$ for $\alpha_t \le 0$ and $\emptyset$ for $\alpha_t \ge 1$. Because a finite rolling window substitutes the largest score in the window at $\alpha_t \le 0$ (setting `.saturated = True`) and the smallest score at $\alpha_t \ge 1$, $\alpha_t$ is never clipped at $[0, 1]$ but is bounded at Lemma 4.1's theoretical envelope $[-\gamma, 1 + \gamma]$ (**[D]**, D18) so finite-window extremes cannot cause unbounded wind-up during regime shifts.

**What each method guarantees.**

- CQR guarantees marginal coverage of at least $1 - \alpha$ when calibration and test points are exchangeable (CQR paper, Theorem 1). Time series generally violate this, and overlapping forecast windows are dependent, so the guarantee is approximate here. The library reports empirical coverage on a held-out period rather than asserting the nominal level.
- ACI makes no distributional assumption; its long-run average miscoverage converges to $\alpha$, with the gap bounded by $(\max\{\alpha_1, 1 - \alpha_1\} + \gamma) / (T\gamma)$ after $T$ steps (ACI paper, Proposition 4.1). It guarantees nothing for any single period.
- After the anchor-aware repair (D17), calibrated pairs can only widen relative to each other (so every calibrated pair covers at least as often as its own CQR offset); uncalibrated interior levels may be pulled inward to stay inside a narrowed calibrated pair.

### 5.3 Anti-forgetting: replay and distillation

Implemented in Phase 4 (`ReplayConfig`, `SyntheticReplaySource`, `distillation_loss`). All of this is our design **[D]**; Mistral has not released its synthetic corpus, so "replay" here cannot mean replaying Mistral's pretraining data.

- **Replay mixing.** When `replay_config: ReplayConfig` is passed to `TimestralTrainer`, each training step draws a replay micro-batch from `replay_dataset` (a user-supplied `TimeSeriesDataset`, or a default seeded `SyntheticReplaySource` covering trend+seasonality, random walks, stationary AR(1)/AR(2), regime shifts, and positive seasonal patterns across log-uniform scales) and combines losses as `(1 - replay_fraction) * L_domain + replay_fraction * L_replay + distill_weight * L_distill`. `ReplayConfig()` defaults to light label-free distillation (`replay_fraction=0.0, distill_weight=0.1, smooth_beta=1e-3`), measured across `head_only`, `lora_temporal`, and `full_ft` (`docs/BENCHMARKS.md` §5). Running replay as a separate micro-batch allows heterogeneous covariate layouts and horizons between domain and replay data (decision D21). `replay_dataset` must not be `val_dataset`. Built-in generators are a regulariser only and make no claim to match Mistral's priors.
- **Distillation to the frozen base.** On replay samples, `distillation_loss` penalises the smooth L1 (Huber, controlled by `ReplayConfig.smooth_beta`, default `1e-3`; exact L1 when `0.0`) difference between the tuned model's and the frozen base model's normalised quantiles, weighted by `distill_weight` (decision D21). This needs no target labels: its mask covers all real target rows inside the requested unpadded horizon, excluding covariates, right-padding steps, and shape-bucketed dummy series. **Frozen-base semantics on resume:** for LoRA modes, the frozen base is always the unadapted base model (`disable_lora`), even when resuming from `load_lora`; for `head_only` and `full_ft`, it is the starting `model` passed to `TimestralTrainer`. **Memory:** `head_only` keeps only a frozen `model.head` copy; LoRA uses CPU-cached step-0 base quantiles (up to 256 MiB, dual `+x`/`-x` when `sign_flip` is on) or zero-extra-VRAM `disable_lora` fallback; `full_ft` uses CPU-cached base quantiles within the 256 MiB cap and falls back to a full frozen model copy on the device when `cache_base_outputs=False` or above the cap (in multi-process mode, teacher caches are skipped and `ReplayConfig.batch_size` is per rank; see §5.6). **Measured ablation with built-in synthetic replay (`docs/BENCHMARKS.md` §5, `docs/VERIFICATION.md` §15) [V]:** on `head_only` retail, default `distill_weight=0.1` strictly beats the lower-LR `1e-3` control on both wQL and forgetting (`5M` 3/3 seeds: `0.2105 / +2.5%` vs `0.2114 / +3.6%`; `28M`: `0.2079 / +3.6%` vs `0.2090 / +4.2%`); on `5M head_only` volatility (3 seeds), `replay_fraction=0.25` beats plain `1e-3` at matched wQL (`0.2231 / +5.0%` vs `0.2236 / +7.8%`), while on `28M` vol (1 seed) plain `1e-3` gives lower wQL (`0.2169` vs `0.2195–0.2196`). On `lora_temporal=3e-3` (3 seeds), `distill_weight=0.1` eliminates the `+31.3%` forgetting cliff (`+0.6%` worst-seed) and edges out shipped `1e-3` on 3/3 seeds (`0.2178` vs `0.2186`, small margin relative to seed spread). On `full_ft=3e-4` retail (3 seeds), neither synthetic pinball (`+4.1%` at 64 series; `+2.8%` at 256 series) nor `distill_weight=0.1` (`0.1999`, worst `+1.3%`) beats simply lowering the learning rate to `2e-4` (`0.1995`, worst `+1.3%`). Real general-domain replay datasets are untested.
- **Forgetting metric.** Raw-space evaluation (`timestral_tune.utils.evaluate_forgetting` / `compute_forgetting`) reports the absolute and relative change in pinball loss, wQL, and MASE (tuned minus zero-shot) on a held-out general set that is not from the target domain (macro-averaged equally across domains in benchmarks so high-magnitude series do not dominate; decision D20). This runs across all modes from Phase 3 onward, independent of whether replay is enabled; `TimestralTrainer` itself logs training/validation loss only and leaves raw-space target and forgetting evaluation to `utils/metrics.py`.
- **Sign-flip augmentation.** The upstream forecaster averages each forecast with the reflected forecast of the negated series by default **[U forecaster.py:221-227]**. Fine-tuning on one-signed data can make the two passes disagree. Randomly negating whole series (targets and covariates together, `p = 0.5`) during training keeps them coherent. **On by default (`TrainingConfig.sign_flip=True`)** from Phase 3 onward (decision D19): verified on `123M` and `209M` across 3 seeds to improve one-signed volatility and retail validation wQL by up to 6.7% while staying within seed spread (improving 5/6 cells) on signed 20-bar log returns **[V]**. In `head_only` with `cache_frozen_features=True`, both `+x` and `-x` orientations are cached on CPU within the 256 MiB cap.

### 5.4 Trainer

- **Forward pass.** The trainer never calls `forecast`. It builds the same inputs as upstream's `_assemble_rows` **[U forecaster.py:332-394]**, runs the two-stream transformer, and takes normalised quantiles at the horizon prediction tokens of target rows.
- **Optimiser.** AdamW with cosine decay and linear warm-up. Sweep-backed default learning rates (`docs/BENCHMARKS.md` §2, decision D19): `3e-3` for `head_only` and `lora_variate`, `1e-3` for `lora_temporal` (`r=8, alpha=16, targets=("q", "k", "v", "o")`), and `1e-4` for `full_ft` **[V]**. As a user recommendation (not a default), setting `learning_rate=3e-4` for `full_ft` on `5M` and `28M` gave lower error (three seeds on `5M`, one seed on `28M`, mainly on volatility for `28M`) at the cost of roughly two to three percentage points more forgetting; keep `1e-4` on `123M` and `209M`, where the two rates tie or favour `1e-4` on validation and `1e-4` forgets less (`docs/BENCHMARKS.md` §2.2).
- **Sign-flip augmentation.** `TrainingConfig.sign_flip=True` by default (decision D19); randomly negates whole series (targets + covariates together, `p=0.5`) during training to match upstream's `symmetric_averaging=True`. Verified across 3 seeds on `123M` and `209M` (`docs/BENCHMARKS.md` §2.1, `docs/VERIFICATION.md` §14): stays within seed spread on signed `logret_20` returns while cutting retail validation wQL by 5.9%–6.7% and volatility wQL on 3/3 seeds **[V]**.
- **Precision.** `bf16` autocast on CUDA (verified on an NVIDIA L4 and on one NVIDIA GeForce RTX 3060 on the 4-GPU host **[V]** across all four trainable modes via `test_bf16_training_on_cuda`, `docs/VERIFICATION.md` §13; raises on CPU, MPS, and non-bf16 GPUs); `fp32` on CPU and on the Apple GPU. The head already promotes to at least fp32 **[U model.py:96]**, statistics run in float64 without gradients **[U scaler.py:28-29]**, and `pinball_loss` promotes to float32. The paper reports bf16 inference within 0.2% of fp32 **[P §4.3]**; in one-off 20-step L4 training trajectories across 5M and 28M, `bf16` validation loss stayed within 0.1%–0.2% of `fp32` while running 2.0×–2.1× faster on 28M and cutting VRAM by ~30% (`docs/VERIFICATION.md` §13; reproducible via `scripts/probes/step_timing.py --device cuda --bf16`).
- **Attention kernel.** Training uses upstream's attention call with PyTorch's default kernel selection, exactly as upstream inference does. An experimental helper, `timestral_tune.models.forward.attention_context("math")`, switches PyTorch to its unfused kernel for the calls inside it; acceptance test T14 and the gradient probe use it to measure the float32 gradient inaccuracy of §12. Twenty-step L4 CUDA training trajectories across `lora_variate`, `lora_temporal`, and `full_ft` (`docs/VERIFICATION.md` §13) show `fp32` default SDPA and `fp32` unfused math matching in validation loss within 0.0002 (identical to 5 decimal places on 28M), so no public attention-kernel toggle is needed (decision D15).
- **Compilation.** `TrainingConfig.compile_model=True` compiles `model.transformer` with `torch.compile` (`compile_mode="default"` or `"reduce-overhead"`). Under `mode="reduce-overhead"`, `DHFDataCollator` automatically pads partial tail batches into power-of-two shape buckets using zero-weighted, group-isolated dummy series (`pad_batch_to_series`), bounding distinct compiled shapes to $\lceil \log_2 B \rceil + 1$ without dropping data or changing loss/gradients. On L4 CUDA, `bf16 + compile("default")` ran 28M `full_ft` at 59.8 ms / 1.80 GiB (3.3× faster than `fp32`, 45% less VRAM) and `lora_variate` at 42.9 ms / 0.94 GiB (`docs/VERIFICATION.md` §13; `scripts/probes/step_timing.py --device cuda --bf16 --compile default`).
- **Gradient clipping** at 1.0 by default.
- **Dropout.** The base model has none **[P §3.3]**. LoRA dropout applies to the adapter path only.
- **CUDA.** Verified **[V]** on an NVIDIA L4 and on one NVIDIA GeForce RTX 3060 (on the 4-GPU host; PyTorch `2.15.0+cu132`, `fp32` and `bf16`): forecasts match CPU to `1.0e-7`–`3.19e-5` relative on L4 and `1.05e-7`–`3.98e-5` on RTX 3060, T1–T14 and the whole suite pass (`580 passed, 4 skipped` at `89ac249` on Python 3.12 on L4; `735 passed, 4 skipped` including the CPU/`gloo` multi-process suite at `71514a6` on `uv`-selected Python 3.15.2 and at `82a21ca` on Python 3.12.16 on L4; `840 passed, 4 skipped` including `tests/test_multi_gpu_check.py` on Python 3.12.16 on L4 at `d474f82` and on one RTX 3060 of the 4-GPU host at `3ac7c6d`; `docs/VERIFICATION.md` §13), including all four modes with replay/distillation in `fp32` and `bf16`, both cached and live-LoRA `reduce-overhead` compile under CUDA graphs, and released `Timestral-5M` `bf16` replay in `head_only` and `lora_temporal` (`full_ft` on released `Timestral-5M` is covered by `scripts/probes/replay_bf16_parity.py`, not by the suite), `AdamW` runs `fused=True`, `bf16` dual-orientation head caching matches streaming `bf16`, shape-bucketed `reduce-overhead` compiles cleanly on non-divisible datasets, and on L4 `bf16 + torch.compile` speeds up 28M covariate steps 3.1×–3.3× over fp32. Float32 gradients through the default attention kernel are less accurate than on the other devices (up to `1.1e-2` on L4 and `6.67e-3` on RTX 3060 in T14, and up to `1.2e-2` on L4 and `1.3e-2` on RTX 3060 in `gradient_accuracy.py`; §12), though L4 20-step training trajectories match unfused math closely (D15). The environment needs a C compiler and Python headers (§12).
- **Apple GPU (MPS).** Supported in v0.1 by running the four float64 statistics sites of §3.5 on CPU and moving their float32 results to the device **[D]**. The statistics carry no gradients, so this changes nothing in the maths. Measured **[V]**:
  - *Forward parity with CPU:* relative difference of 1.9e-7 to 3.4e-6 for `predict_block` in both layouts, 1e-7 for a 96-step forecast, up to 2e-5 for a 2,100-step block-autoregressive forecast, and 1e-7 with numeric and categorical covariates.
  - *Gradients of the training loss:* within 2e-7 to 2.1e-3 of a float64 reference across the T14 scenarios, against 2e-7 to 3.4e-3 for CPU float32. §12 explains why released weights are not at round-off on any device.
  - *Speed of the full training step* (normalised forward, median-folded frame with its CPU round trip, pinball loss, AdamW; context 1,024, horizon 96, batch 32): between 1.4× and 3.2× faster than CPU across four runs, for both univariate batches and batches with five rows per series. Timings vary from run to run.
  - *Memory:* about 4.5 GiB allocated for 28M with five rows per series at batch 32 (down from 7.3 GiB before D16).
  - *Mixed precision:* no speed-up from `bf16` or `fp16` autocast, and `bf16` moved outputs by 1e-2 to 6e-2, so MPS runs fp32 only and `mixed_precision` other than `"fp32"` raises there.
  - *Requirements and scope:* PyTorch 2.8 or newer. Older versions lack the `cummax` operator on this backend, which upstream's input assembly uses; `resolve_device` skips the Apple GPU under `"auto"` and raises for an explicit `"mps"`. `5M` and `28M` are verified on PyTorch 2.8.0 and 2.15.0; **`123M`, `209M`, and long contexts up to `32,768` steps (`1,024` patches)** are verified on PyTorch **2.15.0** on one 16 GiB Apple M4 machine (`scripts/probes/mps_large_and_long_context.py`, `docs/VERIFICATION.md` §15) **[V]**: `123M` and `209M` match CPU to `9.5e-8..1.1e-6` forward and `4.5e-6..8.0e-6` gradient vs float64 reference (cleaner than CPU fp32), and `209M` completes one finite optimiser step in `full_ft` at `32,768` steps (`B=1`, `6.09 GiB` driver) and `cov3` `lora_temporal` at `16,384` steps (`6.10 GiB` driver; long-context gradient parity is untested).
- **Device shims.** The offload is implemented as subclasses outside `_vendor/` that move tensors to CPU and call the parent: a model subclass overriding `scale`, and a forecaster subclass overriding `_cap_quantiles`, `_refine_block` and `_encode_categorical`. The training forward calls `advancing_block_frames` on CPU directly. No vendored file is edited for this (§6.1).
- **Memory.** With covariates the trimmed single-horizon layout uses `L + 2h` tokens per row (§3.4, decision D16) instead of upstream's `2(L + h)`, cutting covariate activation memory by ~42% on CUDA (5.7 → 3.3 GiB on 28M batch 32) and ~38% on the Apple GPU (7.3 → 4.5 GiB) **[V]**.
- **Frozen-feature caching (`head_only`) [D].** `TrainingConfig.cache_frozen_features=True` (default) precomputes each window's frozen horizon hidden states, anchors, targets, and 3-scalar float64 context Welford summaries (or pre-normalised targets for `true_values`) on CPU up to a 256 MiB cap per dataset, skipping re-execution of the frozen transformer body across epochs and repeated evaluations (decision D16). When `sign_flip=True`, both `+x` and `-x` orientations are cached for the training set (counted together against the 256 MiB cap) and selected per window each step, matching streaming `sign_flip=True` to `< 1e-4` L2. Falls back to streaming above the cap or when disabled.

### 5.5 Evaluation

All reported forecasts go through the vendored upstream `TimestralForecaster` with its defaults (symmetric averaging and non-negative clipping on), so tuned and zero-shot numbers are produced by the same code path.

Metrics, in raw space: MASE, mean weighted quantile loss over the 21 levels, pinball loss, empirical coverage and mean width of the 80% and 90% intervals, and the forgetting metric of §5.3.

- **Contract and preconditions [D] (D25, D29).** Every rank must be constructed with the same model architecture and configuration (`model.config`), parameter and buffer schema, trainable parameter set, training, LoRA, and replay configuration excluding rank-specific `device` and `output_dir`, and datasets (`train_dataset`, `val_dataset`, `replay_dataset`), verified at construction by D29. For the deterministic path (`sign_flip=False`, replay `sign_flip=False`, LoRA `dropout=0`), one optimiser step across $N \ge 2$ ranks on domain shards $\{B_0, \dots, B_{N-1}\}$ (and, when replay is configured, replay shards $\{R_0, \dots, R_{N-1}\}$) matches one single-process step on the union batch $B = \bigcup_{r=0}^{N-1} B_r$ (and $R = \bigcup_{r=0}^{N-1} R_r$) in loss scalar, gradient, clipping decision, and parameter update up to floating-point rounding (for `full_ft` distillation at identical student/teacher weights in `float32`, see the PyTorch `F.linear` dispatch note in §9 and §12). With `sign_flip=True`, replay `sign_flip=True`, or LoRA `dropout > 0`, ranks draw from rank-offset streams (D33), so an $N$-rank run and a one-process run execute the same statistical procedure rather than identical numbers. Reproducing single-process `DataLoader` batch order across different $N$ is not claimed. When no multi-rank process group is active (`not dist.is_available()`, `not dist.is_initialized()`, or `world_size == 1`), the one-process path runs unchanged.
- **Where collectives happen and snapshot semantics [D] (D29, D31).** Collectives happen in `TimestralTrainer.__init__` and `TimestralTrainer.fit()` only; `src/timestral_tune/trainer/distributed.py` is the sole importer of `torch.distributed`. `DistributedContext` snapshots `rank`, `world_size`, `backend`, and `device` at construction: `check_active()` verifies that the process group is still initialised with the same `world_size`, `rank`, and `backend`—running at the start of `fit()` (before mutating trainer state) and before every collective primitive, raising `RuntimeError` otherwise. `export()` uses the construction snapshot so it stays valid after the caller destroys the process group. `load_model()`, `load_forecaster()`, `resolve_device()`, `evaluate()`, `export()`, and public `training_step()` are collective-free; calling public `training_step()` on a multi-process trainer raises `RuntimeError` directing callers to `fit()`.
- **The step and explicit gradient reduction [D] / [V] (D22, D23, D24).** `TimestralModel` defines no `forward`, and training calls `compute_loss` / `training_forward` directly rather than wrapping with `DistributedDataParallel` (whose forward/backward hooks are bypassed by calling `compute_loss(ddp.module, ...)`; `docs/VERIFICATION.md` §16 **[V]**). Construction checks that the trainable parameter list is non-empty and that all trainable parameters share `self.device` and a single dtype. `GradientReducer` is allocated per `fit()` in `_DistributedStrategy.prepare_fit()` and released in `cleanup()` after end-of-fit collectives complete, reusing one flat buffer of `total_numel + len(trainable)` elements across the run. The trailing `len(trainable)` slots carry per-parameter `0.0`/`1.0` presence flags inside the same single `all_reduce(ReduceOp.SUM)`: parameters whose `.grad` is `None` on every rank stay `None` on every rank (so AdamW skips weight decay, matching one-process mode), while parameters with a non-`None` `.grad` on at least one rank receive the summed gradient tensor everywhere (including all-zero tensors such as LoRA `lora_A` at step 0). When all local gradients are present, the post-collective host flag read-back (`.tolist()`) is skipped.

  *Collective-safety invariant:* every branch that changes which collectives a rank executes depends only on globally reduced values (or immutable run configuration identical across ranks), never on rank-local batch state. Each global step inside `fit()` runs through `_DistributedStrategy._run_step` using `ReduceOp.SUM` only (`ReduceOp.AVG` raises on CPU/`gloo` in PyTorch 2.4.0; `docs/VERIFICATION.md` §11) in six named stages (stage 1 runs only when `replay_config is not None`; without replay, stages 2–6 run directly):
  1. *Pre-check (`_precheck_domain_for_replay`, only when `replay_config is not None`):* fetches this rank's domain slice inside `except Exception` (excluding `is_oom_error`), reads local `pre_w_d = 0 if raw_domain is None else raw_domain.num_scored`, and runs one 2-element `float64` `all_reduce(ReduceOp.SUM)` over $[W_d^{(r)}, \text{failed}^{(r)}]$. Checked in order: (i) if $\text{failed}_{\text{tot}} > 0$, runs the conditional `int64` length-$N$ failure collective (`stage="training_step"`), taking precedence over skipping even when all healthy peers have $W_d^{(r)} = 0$, before replay is touched; (ii) if $W_D = 0$, every rank returns skipped immediately without entering stage 2, so no rank advances `DistributedBatchCycle` or touches either flip generator and no stats or gradient collective runs. When `replay_config is None`, stage 1 does not run (zero extra collectives).
  2. *Local stage (`_run_local_stage`):* protected end to end by `except Exception` (excluding `is_oom_error`). Fetches `raw_domain` when `replay_config is None` (lazily creating the epoch's domain `DataLoader` iterator on the rank's first non-empty slice), then runs `_prepare_domain_batch` (local `num_scored == 0` skips domain sign flip, `batch.validate`, device transfer, and domain forward, mirroring one-process `fit()`). When `replay_config is not None`, fetches `raw_replay` via `DistributedBatchCycle.next_batch()` (returning `None` on empty slices without touching the replay loader) and, when non-`None`, runs `_prepare_replay_batch` (applying `_replay_flip_generator` via `_apply_series_flip` when `_replay_sign_flip` is enabled, CPU validation, and device transfer; no cached teacher lookup). If both prepared batches are `None`, returns all-zero local stats. Otherwise calls `_compute_loss_terms(..., validate=False, replay=prepared_replay)`—so a rank with an empty or zero-scored domain shard still computes its replay pinball and distillation terms—and packs each term via `_term_weighted_sum` into `(count, weighted_sum, raw_val, non_finite)`: domain $(W_d^{(r)}, s_d^{(r)})$, replay pinball $(W_r^{(r)}, s_r^{(r)})$ (computed iff `replay_fraction > 0` and local `replay.num_scored > 0`), and distillation $(M^{(r)}, s_m^{(r)})$ (computed iff `distill_weight > 0`, where $M^{(r)} = N_{\text{real\_targets}}^{(r)} \cdot \min(\text{replay\_dataset.forecast\_horizon}, H_{\text{padded}})$ is the label-free active target-step count). If any term's `val` or `val * count` is non-finite, its `weighted_sum` stays `0.0` (so `NaN`/`Inf` never poisons the SUM collective), $\text{nf}^{(r)} = 1$, and `first_non_finite` records the first non-finite scalar among `(domain, replay, distill)`. If a local non-OOM `Exception` occurs, zeroes all stats and sets $\text{failed}^{(r)} = 1$.
  3. *Reduce statistics (`_reduce_step_stats`):* one 8-element `float64` `all_reduce(ReduceOp.SUM)` over $[W_d^{(r)}, s_d^{(r)}, W_r^{(r)}, s_r^{(r)}, M^{(r)}, s_m^{(r)}, \text{nf}^{(r)}, \text{failed}^{(r)}]$, yielding $[W_D, S_D, W_R, S_R, M_{\text{tot}}, S_M, \text{nf}_{\text{tot}}, \text{failed}_{\text{tot}}]$.
  4. *Decide control flow and active weights (`_decide_step`):* checked in exact order: (i) if $\text{failed}_{\text{tot}} > 0$ (taking precedence over $\text{nf}_{\text{tot}}$), runs the conditional `int64` length-$N$ `raise_propagated_failure(..., stage="training_step")` so failing rank(s) re-raise their original exception and peers raise `RankFailureError` naming failing rank(s) and stage without running backward; (ii) if $\text{nf}_{\text{tot}} > 0$, every rank raises `FloatingPointError` without running backward (failing rank formats `first_non_finite`, healthy peers format `"non-finite"`); (iii) if $W_D = 0$, every rank skips the step with exact one-process skip semantics (no backward, no optimiser/scheduler step, `global_step` unchanged, `skipped_batches` incremented, and `RuntimeError` on every rank if a whole epoch produces no optimiser step); (iv) with $f = \text{replay\_fraction}$ (or $0$) and $\lambda = \text{distill\_weight}$ (or $0$), sets `replay_active` iff $f > 0 \wedge W_R > 0$, `distill_active` iff $\lambda > 0 \wedge M_{\text{tot}} > 0$, and $w_{\text{dom}} = 1 - f$ if `replay_active` else $1.0$ (so globally unscored replay $W_R = 0$ falls back to full domain weight $1.0$ while keeping label-free distillation active when $\lambda > 0 \wedge M_{\text{tot}} > 0$, matching one-process `_mix_loss_terms`). Computes $\text{global\_loss} = w_{\text{dom}} \frac{S_D}{W_D} + \mathbb{1}_{\text{replay\_active}} f \frac{S_R}{W_R} + \mathbb{1}_{\text{distill\_active}} \lambda \frac{S_M}{M_{\text{tot}}}$ and checks `math.isfinite(global_loss)`, raising `FloatingPointError` if non-finite.
  5. *Local backward (`_backward_local_terms`):* forms this rank's active weighted terms:
     $$\tilde{\mathcal{L}}^{(r)} = \mathbb{1}_{W_d^{(r)} > 0}\, w_{\text{dom}} \frac{W_d^{(r)}}{W_D}\, L_d^{(r)} + \mathbb{1}_{\text{replay\_active} \wedge W_r^{(r)} > 0}\, f \frac{W_r^{(r)}}{W_R}\, L_r^{(r)} + \mathbb{1}_{\text{distill\_active} \wedge M^{(r)} > 0}\, \lambda \frac{M^{(r)}}{M_{\text{tot}}}\, L_m^{(r)}$$
     and calls `.backward()` iff at least one term is active locally (ranks with no active local term skip `.backward()`, leaving local `.grad` as `None`).
  6. *Reduce gradients and update (`_reduce_gradients_and_update`):* captures `learning_rate`, runs `GradientReducer.reduce()` (packing trainable gradients and presence flags into the reused flat buffer, running one `all_reduce(ReduceOp.SUM)` without dividing by $N$, unpacking into `p.grad`), clips (`clip_grad_norm_`), and steps AdamW and the scheduler.

  Per active step in `fit()`, this executes 2 collectives in `_run_step` (stats + grad) plus 1 `broadcast_status` in `on_step_end` without replay (3 total), or 3 collectives in `_run_step` (pre-check + stats + grad) plus 1 `broadcast_status` in `on_step_end` with replay (4 total); globally skipped steps execute 1 collective (stats without replay; pre-check with replay).

  *Exception-propagation rule [D]:* single-rank failure propagation (at `__init__` startup and consistency checks, in the pre-check domain fetch and step local stage, in sharded validation, and in rank-0 callbacks/post-validation) catches `Exception` only—never `BaseException`—and immediately re-raises `is_oom_error(exc)` (`torch.OutOfMemoryError` and `torch.cuda.OutOfMemoryError` by type, without string-matching generic `RuntimeError`) without entering a collective. Failing rank(s) re-raise their original exception; healthy peers raise `RankFailureError` (a picklable `RuntimeError` subclass exported from `timestral_tune.trainer`, carrying `.failing_ranks` and `.stage`). Verified on CPU/`gloo` in T15(d), T15(i), T15(l), and `tests/test_distributed.py`; device-binding errors, OOM, backward failures, post-broadcast `__init__` failures, killed processes, and broken device contexts are not propagated and end by launcher teardown or process-group timeout (D35). Observed peer-death behaviour per backend (`scripts/probes/distributed_rank_failure_check.py`, single-L4 sessions at `8e8f490` and `d474f82` plus separate-GPU 4× RTX 3060 session S6 at `3ac7c6d`, `docs/VERIFICATION.md` §17.4 **[V]**; PCIe/SHM transport on S6 was a one-off session-harness observation): on CPU/`gloo`, surviving ranks raise a Python `RuntimeError` (promptly on TCP transport reset on Linux x86_64, or at the process-group timeout on macOS arm64) and unwind through `except`/`finally`; on CUDA/NCCL (both on one shared NVIDIA L4 and on 2 or 4 separate RTX 3060 GPUs), surviving ranks are killed by `SIGABRT` after the process-group timeout plus NCCL's health-check wait with no Python exception raised, so `except`/`finally` blocks inside `fit()` and user code do not run. Neither backend hung; NVLink / GPU P2P NCCL rank-failure behaviour remains untested.
- **Why count weighting [D] / [V] (D24).** `pinball_loss` (§4.2) and `distillation_loss` (§5.3) average equally over active positions, so the union-batch loss for each term is the count-weighted sum of rank means:
  $$\mathcal{L}_d(B) = \frac{1}{|\mathcal{Q}|\, W_D} \sum_{r=0}^{N-1} \sum_{i \in B_r} w_i \sum_{\tau \in \mathcal{Q}} \rho_\tau(z_i - \hat{q}_{\tau, i}) = \sum_{r=0}^{N-1} \frac{W_d^{(r)}}{W_D}\, L_d^{(r)}, \qquad W_D = \sum_{r=0}^{N-1} W_d^{(r)},$$
  and identically $\mathcal{L}_r(R) = \sum_r \frac{W_r^{(r)}}{W_R} L_r^{(r)}$ and $\mathcal{L}_m(R) = \sum_r \frac{M^{(r)}}{M_{\text{tot}}} L_m^{(r)}$; by linearity of differentiation, scaling each active local term by its global weight and count share yields the exact union-batch gradient after `ReduceOp.SUM`. Equal-weight averaging $\frac{1}{N} \sum_r \nabla_\theta L^{(r)}$ disagrees whenever active counts differ across ranks (`docs/VERIFICATION.md` §16–§17 **[V]**).
- **Sampling, replay cycling, workers, and batch size [D] (D26, D27, D36, D37).** `DistributedBatchSampler` generates one global permutation of `0..len(dataset)-1` per epoch (natural order when `shuffle=False`; when `shuffle=True`, SHA-256 of `"timestral-tune:epoch:{seed}:{epoch}"` truncated to a 63-bit integer seeding `torch.randperm`, avoiding `seed + epoch` aliasing). Within each global batch, rank `r` takes the `r`-th contiguous slice: full iterations assign each rank `batch_size` indices, and a trailing partial batch of length $R = \text{len}(\text{dataset}) \bmod (N \cdot B) > 0$ assigns rank $r$ a contiguous run of $\lfloor R / N \rfloor + \mathbb{1}_{r < R \bmod N}$ indices, leaving a rank empty only when $R < N$ and $r \ge R$. Every rank runs $\lceil \text{len}(\text{dataset}) / (N \cdot B) \rceil$ global iterations per epoch (`DistributedBatchSampler.num_global_steps` and `.slice_size(step)`); `total_steps`, the LR schedule, `max_steps`, `eval_every`, and `log_every` count global optimiser steps. `DistributedBatchSampler` yields only non-empty slices, so `DHFDataCollator` is never called empty and `num_workers > 0` / `persistent_workers=True` work cleanly. Each rank creates its domain `DataLoader` iterator lazily on its first non-empty slice of the epoch (ranks that stay empty when `len(dataset) < N` never create an iterator), and both the multi-process training and sharded validation loaders receive an explicit `torch.Generator` seeded with `rank_seed(config.seed, rank)` so loader iteration does not consume PyTorch's global RNG stream (LoRA dropout).

  *Replay sampling & `DistributedBatchCycle` (D37):* when `replay_config is not None`, `prepare_fit()` builds a second `DistributedBatchSampler` over `replay_dataset` with per-rank batch size $b = \text{replay\_config.resolved\_batch\_size}(B)$, `shuffle=config.shuffle`, and **shared** epoch-permutation seed `config.seed + 2_000_009`, paired with a `DataLoader` seeded with `rank_seed(config.seed + 2_000_009, rank)` (isolating global RNG) and wrapped in `DistributedBatchCycle`. Every active global step calls `next_batch()` in lockstep: at `step_in_epoch == 0`, `set_epoch(replay_epoch)` updates the global permutation and resets the iterator; non-empty slices lazily create `iter(replay_loader)` and draw the next batch; empty slices return `None` without touching the loader; reaching `num_global_steps = ceil(len(replay_dataset) / (N * b))` wraps to `replay_epoch += 1` independently of domain epochs. When `len(replay_dataset) < N * b`, `num_global_steps == 1`, so replay wraps every active step using the balanced trailing split; when `len(replay_dataset) < N`, ranks $r \ge \text{len}(\text{replay\_dataset})$ have empty replay slices on every step, receive `None`, and never call `iter(replay_loader)`. Calling `fit()` again creates a fresh replay sampler and cycle starting at replay epoch 0, step 0.

  *Workers (D36):* the replay `DataLoader` always runs in the main process (`num_workers=0`, `persistent_workers=False`) regardless of `config.num_workers`, matching the one-process `_replay_loader`. With `config.num_workers > 0`, each rank therefore keeps at most two persistent worker pools during `fit()` (training, plus sharded validation when `val_dataset` is given).

  *Per-rank batch sizes & startup logs (D27):* both `TrainingConfig.batch_size` ($B$) and `ReplayConfig.batch_size` ($b$) are per rank, giving effective domain batch $N \cdot B$ and effective replay batch $N \cdot b$. When `ReplayConfig.batch_size is None`, resolution uses each rank's `TrainingConfig.batch_size` (`max(1, round(B * replay_fraction))` when `replay_fraction > 0`, else `max(1, B // 4)`), so $N \cdot \text{resolved}(B)$ can differ from $\text{resolved}(N \cdot B)$ due to rounding or the minimum of 1 (pass an explicit `ReplayConfig.batch_size` when matching a specific one-process global replay batch). At construction, rank 0 logs `world_size`, `backend`, `per_rank_batch_size`, and `effective_batch_size`—appending `per_rank_replay_batch_size` and `effective_replay_batch_size` when `replay_config` is set—and emits `logger.warning` when `learning_rate is None` and $N \cdot B > 32$, with no automatic LR scaling (non-zero ranks emit no duplicate startup notices).
- **Devices and backend [D] (D28).** The caller owns process-group lifecycle (`torchrun` / `dist.init_process_group`), and `TimestralTrainer` activates multi-process mode via `DistributedContext.detect(config.device)` when `dist.is_available()`, `dist.is_initialized()`, and `world_size > 1`. `resolve_device()` stays pure and unchanged. Backend and device checks run **before any collective and outside failure propagation**:
  1. `dist.get_backend()` is checked by exact string equality: only `"gloo"` or `"nccl"` is accepted (device-qualified forms such as `"cpu:gloo"` raise `ValueError`).
  2. For `"gloo"`, `config.device` must be `None`, `"auto"`, `"cpu"`, or `torch.device("cpu")` (no index); anything else raises `ValueError`. For `"nccl"`, an explicitly indexed CUDA device (e.g. `"cuda:1"` or `torch.device("cuda", 1)`) is honoured; otherwise any of `None`, `"auto"`, `"cuda"`, or unindexed `torch.device("cuda")` selects `cuda:LOCAL_RANK` (`LOCAL_RANK` must parse as an integer) or `cuda:rank` when `LOCAL_RANK` is unset, validates `0 <= index < torch.cuda.device_count()`, and binds with `torch.cuda.set_device(index)` before anything querying the current device (notably `torch.cuda.is_bf16_supported()`). (Note: `TrainingConfig.device` is currently annotated `str = "auto"`; see §12.) In Stage 3 session S6 on **4× NVIDIA GeForce RTX 3060** (`3ac7c6d`, `--device-map per-rank`, `NCCL_MULTI_RANK_GPU_ENABLE` unset; `docs/VERIFICATION.md` §17.4 **[V]**), the tracked probes exercised the default `device="auto"` → `cuda:LOCAL_RANK` branch live (`cuda:0..1` for `N = 2` and `cuda:0..3` for `N = 4`), alongside earlier single-L4 shared-GPU runs (`device="cuda:0"`, `--device-map shared`); all other branches of `_resolve_rank_device` (`None`, `"cuda"`, unindexed `torch.device("cuda")`, `LOCAL_RANK`-unset fallback to `cuda:rank`, and other explicitly indexed CUDA inputs) remain unit-tested with mocks in `tests/test_distributed.py` only.
- **Loading, startup checks, broadcast, and teachers [D] (D29, D32).** Every rank calls `load_model()` with no rank-0 download barrier. Source inspection confirms vendored `resolve_checkpoint` delegates through `snapshot_download` to `hf_hub_download` with per-file `WeakFileLock` serialisation in both installed `huggingface_hub 2.4.0` and the `0.23.0` dependency floor (`docs/VERIFICATION.md` §12; source reading only, not a concurrent-download test). After backend validation, device binding, and context snapshotting, `TimestralTrainer.__init__` runs five steps:
  - **(a) Rank-local setup & digest** inside `except Exception` (OOM re-raised immediately): `bf16` check, multi-process restriction check (`compile_mode="reduce-overhead"` refused only when `compile_model=True`), `lora_config` and `replay_config` / `replay_dataset` validation (including constructing the default 64-series `SyntheticReplaySource` with shared seed `config.seed + 2_000_003` when `replay_config is not None` and `replay_dataset is None`), model loading or caller-supplied `model` validation, dataset checks (including non-empty `replay_dataset`), `_select_trainable()`, non-empty/single-device/single-dtype trainable checks, `early_stopping_patience`/callback validation, and `_startup_consistency_digest()` (so a single-rank digest error propagates cleanly via step (b) without hanging peers).
  - **(b) Startup failure collective:** `int64` length-$N$ `all_reduce(ReduceOp.SUM)` (`stage="startup"`); failing rank(s) re-raise their original exception and peers raise `RankFailureError`.
  - **(c) Consistency check:** the SHA-256 digest hashes canonical JSON over `model.config.to_dict()`, sorted parameter and buffer `(name, shape, dtype)`, trainable parameter names in order, `TrainingConfig` fields excluding `device` and `output_dir`, `lora_config` and `replay_config` dicts (or `None`), and each present dataset's (`train_dataset`, `val_dataset`, `replay_dataset`) length and `dataset_fingerprint`. `check_consistency()` hashes the bytes into 4 signed `int64` words, broadcasts rank 0's digest, compares locally, and runs an `int64` length-$N$ failure collective (`stage="startup_consistency"`): mismatched rank(s) raise `ValueError` and matching peers (including rank 0 when another rank mismatches) raise `RankFailureError` naming the mismatched rank(s) and stage.
  - **(d) Initial-state broadcast:** `broadcast_module_state()` broadcasts every unique parameter and buffer in sorted-name order from rank 0 (staging non-contiguous or off-device tensors through `ctx.device`), aligning caller-supplied `model=` weights and buffers across all modes.
  - **(e) Post-broadcast setup:** `_setup_replay_teacher()` (so frozen teachers reflect rank 0's broadcast weights, before `torch.compile`), `torch.compile`, optimiser and scheduler setup, and one-time rank-0-only startup logs (effective batch sizes, default-LR `logger.warning` above effective domain batch 32, `head_only` cache-bypass `logger.info` when `cache_frozen_features=True`, and teacher cache-bypass `logger.info` when `replay_config` has `distill_weight > 0`, `cache_base_outputs=True`, and `mode != "head_only"`).

  *No caches & live teacher paths (D32):* in multi-process mode, neither the `head_only` frozen-feature caches (`_train_head_cache`, `_val_head_cache`, `_replay_head_cache`; `_get_head_cache()` always returns `None`) nor the frozen-base teacher output caches (`_replay_base_pos`, `_replay_base_neg`) are built. When `distill_weight > 0`, each mode runs its uncached teacher path:
  - `head_only`: deep-copies `self.model.head` into `_frozen_head` on `self.device` (`eval()`, `requires_grad=False`) and evaluates it under `torch.no_grad()` on the streaming replay forward's horizon hidden states (no second transformer pass; minimal extra memory).
  - `lora_variate` / `lora_temporal`: keeps `_frozen_head = None` and `_frozen_base = None`, running a live zero-extra-VRAM second forward on `self.model` under `eval()`, `torch.no_grad()`, and `disable_lora(self.model)` (restoring `self.model.training` in `finally`).
  - `full_ft`: deep-copies the full `self.model` into `_frozen_base` on `self.device` (`eval()`, `requires_grad=False`) and runs `training_forward(self._frozen_base, replay_batch, validate=False)` under `torch.no_grad()`. **Memory implication:** every rank holds a full live frozen copy of all model weights on its device alongside the trainable model (roughly doubling model weight memory per rank, on top of `GradientReducer`'s flat gradient buffer; §12).
- **Seeding and timeouts [D] (D33, D35, D37).** Domain epoch permutation (`config.seed`), LoRA initialisation (`config.seed`), default `SyntheticReplaySource` (`config.seed + 2_000_003`), and replay epoch permutation (`config.seed + 2_000_009`) share seeds across ranks. Rank-offset streams use `rank_seed(base, rank)`: rank 0 keeps single-process `base` unchanged (`config.seed` for global `torch.manual_seed` / LoRA dropout and train/val `DataLoader` generators, `config.seed + 1_000_003` for domain `sign_flip`, `config.seed + 2_000_009` for the replay `DataLoader` generator, and `config.seed + 3_000_007` for replay `sign_flip`), while rank $r > 0$ uses `(base + r * 1_000_000_007) % 2^63`. Replay sign flips inherit `config.sign_flip` when `replay_config.sign_flip is None` and are applied once in `_prepare_replay_batch` so student and frozen teacher see identical orientations. Unpropagated failures end by launcher teardown or process-group timeout; callers should pass an explicit `timeout` to `init_process_group` (D35), noting that on NCCL (observed in `scripts/probes/distributed_rank_failure_check.py` on both single-L4 shared NCCL and separate-GPU 4× RTX 3060 NCCL) peer death terminates surviving ranks via `SIGABRT` without running Python `except`/`finally` blocks (whereas `gloo` raises a Python `RuntimeError`—promptly on TCP transport reset on Linux x86_64, or at the process-group timeout on macOS arm64; `docs/VERIFICATION.md` §17.4 **[V]**).
- **Rank 0's role, end of `fit()`, and cleanup timing [D] (D30).** `on_fit_start` runs inside `fit()`'s `try/finally`. Callbacks (`ProgressLogger`, `EarlyStopping`, user callbacks), best-loss tracking, best-weights copy, early stopping, and restore decisions run on rank 0 only, with the post-validation block protected by failure propagation. All control broadcasts use fixed-size `float64` `[code, value]` tensors (`ControlStatus` in `{CONTINUE, STOP, FAILED}`). On every non-zero rank, `self.should_stop` is unconditionally assigned `status is ControlStatus.STOP` after each rank-0 hook broadcast, mirroring both setting and clearing `should_stop` across hooks (preventing collective deadlock if `on_evaluate` clears a flag set in `on_step_end`). `on_step_end` propagates rank 0's step loss and `on_evaluate` propagates rank 0's validation loss, which non-zero ranks record in `train_history` and `eval_history`; `on_fit_end` broadcasts final status so `fit()` returns or raises together on every rank. `self.model.eval()` runs in the inner `finally` before `finalize_best()` (which, only when `val_dataset is not None`, broadcasts `[has_best, best_eval_loss, best_step, restored]` and each restored trainable parameter when `restored == 1`) and `on_fit_end()`; `strategy.cleanup()` (releasing `GradientReducer`, train/val/replay loaders and samplers, `DistributedBatchCycle`, and both flip generators) runs in an outer `finally` **after** `on_fit_end()`'s broadcast completes so asymmetric `DataLoader` worker shutdown cannot stall end-of-fit collectives. All ten `TrainingResult` fields are equal across ranks by construction.
- **Validation, `evaluate()`, and `export()` [D] (D31).** Internal validation inside `fit()` uses its own lazy, cached stride loader (`validation_shard_indices`: `r, r+N, ...`, never touching `self._val_loader`, skipped on ranks with empty shards, given a rank-seeded `torch.Generator`), `eval_batch_size` per rank, `eval()`/`no_grad()` restoring `self.model.training` in `finally`, and one end-of-eval `float64` `ReduceOp.SUM` over `[loss_sum, scored_positions, batches, failed]` (followed by the length-$N$ `int64` rank vector only if `failed > 0`). Empty or zero-scored shards contribute zeros, and `ValueError("the dataset has no scored position to evaluate")` is raised on every rank only from the global count. `EvalResult.loss` and `EvalResult.scored_positions` match one-process `evaluate()`, while `EvalResult.batches` is the sum of per-rank batch counts. Public `evaluate()` is rank-local and collective-free. Public `export()` is collective-free, uses the construction snapshot, and runs shared `_validate_export_inputs` on every rank without calling `dataset_fingerprint()` on either `train_dataset` or `replay_dataset` on non-zero ranks (only validating caller-supplied `data_fingerprint` if given). Rank 0 writes the export directory and adds top-level `world_size` and `effective_batch_size` keys to `tune_metadata.json` when `world_size > 1`, alongside `replay_config` and `replay_source` on replay runs (§7.4; per-rank `batch_size` stays in `hyperparameters["batch_size"]` and `replay_config["batch_size"]`, with no `effective_replay_batch_size` key); non-zero ranks log that rank 0 writes the directory, write nothing, and return `Path(target)`. Multi-process scripts reading exported files from non-zero ranks must synchronise themselves (e.g. `dist.barrier()`).
- **Remaining restrictions and scope [D] (D32, D34).** In multi-process mode: `compile_mode="reduce-overhead"` raises `ValueError` when `compile_model=True` (`compile_mode="default"` is allowed, smoke-tested on CPU/`gloo` both without replay and with LoRA replay + live `disable_lora` distillation, and exercised under `torchrun` on both one shared NVIDIA L4 and 4 separate RTX 3060 GPUs at `N = 2` and `N = 4` across `tiny_random`, `5M`, and `28M`, `docs/VERIFICATION.md` §17.4 **[V]**; NVLink/P2P, separate-GPU run-to-run compiled reproducibility, and scaling remain in Stage 3); public `training_step()` raises `RuntimeError`; unsupported backends or backend/device mismatches raise `ValueError`; stale/changed process groups raise `RuntimeError`; and neither `head_only` frozen-feature caches nor frozen-base teacher output caches are built. `nn.DataParallel`, third-party wrappers (`accelerate`, `lightning-fabric`), multi-node training, and benchmark-script edits remain out of scope (D34).

### 6.1 Dependency on upstream: vendored **[D]**

`timestral` is not on PyPI, and PyPI rejects packages that depend on a git URL. The PyPI name `timestral` is also unclaimed, so a bare requirement on it would be a dependency-confusion risk. Training additionally needs upstream's private functions, which a version pin cannot protect.

- `scripts/vendor_upstream.py` copies the upstream package into `src/timestral_tune/_vendor/timestral/` at the pinned commit, with its Apache 2.0 `LICENSE`. The repository `NOTICE` names the source and commit.
- **One mechanical modification is made:** upstream's files import each other absolutely (`from timestral.config import …`), which would fail, or silently resolve to an installed official `timestral`. The script rewrites these to relative imports and adds a notice header to each of the five files it changes. The other four source files are byte-identical. A manifest records the pristine and vendored hash of every file.
- All new logic lives outside `_vendor/` and imports from it. Vendored files are never edited by hand; a test compares them with the manifest.
- A scheduled CI job runs `scripts/check_upstream_drift.py`, which compares upstream `main` with the manifest's pristine hashes and fails on drift.
- Parameter names are never changed, so exported weights load in the official package with `strict=True` **[U loading.py]**.

### 6.2 Data contract

- **Input.** A long-format frame with one row per (series, timestamp), an id column and a time column. Each series must be regularly sampled; gaps become missing values.
- **Roles.** `target_cols`, `past_covariates`, `known_covariates`, and their categorical counterparts. The name `known_covariates` follows upstream.
- **Windows.** A window is a forecast origin plus up to `context_length` steps before it and `forecast_horizon` steps from it. Origins are anchored at the end of each series and step back by `stride`, so the most recent data is always used. A window is dropped, and counted, when no target is observed in its context or in its horizon.
- **Shape rules.** `context_length` may not exceed the model's context cap (32,768 steps for the released checkpoints); a longer one raises instead of being truncated, so that nothing is dropped silently. Every window of a dataset is left-padded with unobserved zeros to `context_length` rounded up to a whole patch, so all batches have one shape. Upstream pads each call only to the next multiple of 32 **[U forecaster.py:70-77]**; the extra padding is never attended to and leaves forecasts unchanged within 1e-5 **[V]**. The horizon is rounded up to whole patches; padded steps get zero loss weight. `forecast_horizon` must be at most 1,024 for training.
- **Preprocessing parity.** Target rows are forward-filled with the observation mask preserved; covariate NaNs become unobserved zeros. Apart from the extra left padding above, the collated tensors equal those of upstream's `_assemble_rows` **[V]**.
- **Storage.** Frames from polars, pandas or pyarrow are converted once to contiguous float32 arrays per series; none of the three is a runtime dependency. A window's numeric arrays are views into those arrays, its category codes are renumbered copies (§6.3 rule 4), and the collator makes the padded copies.
- **Validation.** Null ids or timestamps, duplicate (series, timestamp) pairs, timestamps off the regular grid, non-numeric or infinite values and time-zone-aware timestamps raise. `regularize=False` treats consecutive rows as consecutive steps, for calendar-irregular data such as monthly series.

### 6.3 Point-in-time rules

1. Target values after the forecast origin are labels only. They are never model inputs.
2. Past-only covariates are cut at the origin. The user is responsible for supplying values as they were known at each timestamp; a per-column `available_lag` shifts a covariate that is published late.
3. Known-future covariates must be genuinely known in advance over the horizon.
4. Categorical covariates are target-encoded **per window, using the context only**, with horizon codes looked up in the context's table. This matches upstream inference exactly **[U covariate_encoding.py]**, **[U forecaster.py:246-276]**. Series with several target variates have no single target to encode against, so the category codes go to the model as numbers, as upstream does **[U forecaster.py:264-267]**. The numbering must then not depend on the future either: each window numbers its categories by rank among the categories it can see (context for past-only covariates, context and horizon for known-future ones), so a category that first occurs after the origin or after a split cutoff cannot change a window's inputs **[D]**. `window_category_codes` is that rule; apply it to a window's codes before calling upstream's `forecast` on a model trained this way.
5. `split_by_time(cutoff, embargo)` gives training windows nothing at or after the cutoff, context and horizon alike. Validation origins start `embargo` steps after it, and windows that straddle the cutoff are dropped. No validation label can appear in a training window even with `embargo=0`; the embargo adds a gap for strongly dependent data.

Saved LoRA adapters can be re-attached to a base model (and resumed in `TimestralTrainer`) with `load_lora(base_model, export_dir)`.

For multi-process runs (§5.6, D31), `export_checkpoint()` accepts optional keyword arguments `world_size: int | None = None` and `effective_batch_size: int | None = None` (passed together or both omitted; positive integers excluding `bool`, with `effective_batch_size >= world_size`). ### 7.5 Optional Lacuna integration

Installed with `pip install "timestral-tune[lacuna]"`; requires Python 3.11+ and `lacuna-quant>=0.14.1`.

Lacuna consumes signals, prices, returns and experiment history, and itself produces the audit bundle (`report.bundle(...)`). We found no forecast or quantile ingestion in 0.14.1. So this integration writes Lacuna's inputs; it does not write bundles.

- **Trial records.** Each training or evaluation run is appended to a `lacuna.ExperimentRegistry` with `record(parameters=..., metric=..., metric_name=..., data_fingerprint=..., code_fingerprint=..., result_fingerprint=..., metadata=...)`. Model selection is logged with `record_selection(eligible_trial_ids=..., selected_trial_ids=..., metric=..., direction="minimize", used_holdout=...)`. This gives Lacuna the full candidate set for multiple-testing corrections.
- **Signal frames.** A helper writes a long frame with columns `time`, `instrument`, `signal`, which are the default column names of `lacuna.SignalStudy`. The signal is a user-chosen function of the forecast, for example the median or an interquantile spread. The user supplies prices to Lacuna.
- **Deflated Sharpe Ratio.** This needs strategy returns, which a forecaster does not produce. It applies only when the user builds a strategy on the signal and gives Lacuna its returns. `timestral-tune` computes no Sharpe ratios.

### 7.6 Multi-process training (Stages 1–2, experimental)

Launch with `torchrun --nproc_per_node=2 train.py` (or initialise a `"gloo"` / `"nccl"` group directly). Multi-process training is verified on CPU/`gloo` (macOS arm64 and Linux x86_64; `docs/VERIFICATION.md` §17.1), exercised on one NVIDIA L4 with shared-GPU NCCL, and run on **4 separate NVIDIA GeForce RTX 3060 GPUs over PCIe/SHM** via the tracked Stage 3 scripts (`--device-map per-rank`, `docs/VERIFICATION.md` §17.4); Stage 3 overall (T15 on NCCL, NVLink/P2P + cross-GPU determinism, tier calibration, and multi-GPU scaling; §10) remains open, so treat multi-GPU CUDA/NCCL as experimental until Stage 3 completes:

```python
import datetime
import torch.distributed as dist

from timestral_tune import LoraConfig, ReplayConfig, TimestralTrainer, TrainingConfig
from timestral_tune.trainer import RankFailureError

dist.init_process_group(backend="nccl", timeout=datetime.timedelta(minutes=5))  # "gloo" on CPU; Stage 3 open (PCIe/SHM session run; T15 on NCCL & scaling open)
try:
    config = TrainingConfig(
        model_name_or_path="mistralai/Timestral-28M",
        mode="lora_variate",
        device="auto",            # "auto", "cuda", unindexed torch.device("cuda"), or None -> cuda:LOCAL_RANK on nccl
        batch_size=8,             # per rank (effective batch = world_size * 8)
        epochs=5,
        mixed_precision="bf16",   # "fp32" on CPU/gloo
        output_dir="./checkpoints/timestral-28m-ddp",
    )
    lora = LoraConfig(r=8, lora_alpha=16, axes=("variate",), targets=("q", "k", "v", "o"))
    replay = ReplayConfig(replay_fraction=0.0, distill_weight=0.1, batch_size=2)  # per rank; optional
    trainer = TimestralTrainer(config, train_ds, val_ds, lora_config=lora, replay_config=replay)
    result = trainer.fit()        # all ranks enter; TrainingResult matches across ranks
    trainer.export()              # rank 0 writes; non-zero ranks validate and return Path
    if dist.get_rank() == 0:
        final_eval = trainer.evaluate()  # collective-free
except RankFailureError as err:
    # Runs only for propagated Python Exception failures (D23), not NCCL peer death
    print(f"peer rank(s) {err.failing_ranks} failed during {err.stage}")
    raise
finally:
    # Runs on normal exit and Python exceptions (incl. gloo peer-death RuntimeError);
    # does NOT run on NCCL peer death, which aborts surviving ranks via SIGABRT
    dist.destroy_process_group()
```

`RankFailureError` (exported from `timestral_tune.trainer`) is a picklable `RuntimeError` subclass carrying `.failing_ranks: tuple[int, ...]` and `.stage: str`. It is raised on healthy peers only for propagated Python `Exception`s (D23). On unpropagated peer process death (D35), observed behaviour depends on the backend and OS (`scripts/probes/distributed_rank_failure_check.py`, single-L4 sessions at `8e8f490` and `d474f82` plus separate-GPU 4× RTX 3060 session S6 at `3ac7c6d`, `docs/VERIFICATION.md` §17.4 **[V]**; PCIe/SHM transport on S6 was a one-off session-harness observation): on CPU/`gloo`, surviving ranks raise a Python `RuntimeError` (promptly on TCP transport reset on Linux x86_64, or at the process-group timeout on macOS arm64) and unwind normally through `except`/`finally`; on CUDA/NCCL (both on one shared NVIDIA L4 and on 2 or 4 separate RTX 3060 GPUs), surviving ranks are killed by `SIGABRT` after the process-group timeout plus NCCL's health-check wait with no Python exception raised, so neither `except` nor `finally` (including `dist.destroy_process_group()` above and `fit()`'s own cleanup) runs. Neither backend hung; NVLink / GPU P2P NCCL rank-failure behaviour remains untested.

On `"nccl"`, `config.device` set to `"auto"` (the default), `"cuda"`, unindexed `torch.device("cuda")`, or `None` selects `cuda:LOCAL_RANK` (falling back to `cuda:rank` if `LOCAL_RANK` is unset); an explicitly indexed device such as `"cuda:0"` forces that index (D28; note `TrainingConfig.device` is currently annotated `str`, see §12). Both `TrainingConfig.batch_size` and `ReplayConfig.batch_size` are per rank: when `ReplayConfig.batch_size=None`, resolution uses each rank's `TrainingConfig.batch_size`, so `world_size * resolved_batch_size(batch_size)` can differ from `resolved_batch_size(world_size * batch_size)` due to rounding or the minimum of 1 (`config.py`). When `TrainingConfig.num_workers > 0`, each process/rank keeps up to two persistent worker pools during `fit()` (training, plus validation when `val_dataset` is given); the replay loader always runs in the main process (`num_workers=0`).

## 9. Acceptance Tests

These replace the original "assert zero gradients on non-target covariate positions" test, which was mis-specified: a target-only loss produces **non-zero** gradients on covariate inputs **[V]**, and that is intended, since targets read covariates.

**T15 cases (`tests/acceptance/test_distributed.py`, `test_t15_*`, 19 test functions / 34 collected items, CPU/`gloo` default and opt-in CUDA/`nccl` via `TIMESTRAL_TEST_DIST_BACKEND=nccl`, `N=2` and `N=4`, tiny random model) [D].** For `float64` tiers, cases `(a)`, `(g)`, `(j)`, and `(k)` pass a `float64` model under `float64_reference()` (`tests/helpers.py`, float64 RMSNorm) directly through `fit()` (with `TimeSeriesDataset`'s `float32` inputs); `(b)`, which constructs batches directly, converts batch inputs to `float64` (`as_double`).

*Shared tolerance tiers and headroom knob (`tests/distributed_harness.py`) [D] / [V]:* all five parity tiers for T15 and `tests/test_trainer_distributed_replay.py` are defined in one place (`tests/distributed_harness.py`):

| Tier | `float64` | `float32` (at scale `1.0`) | What it bounds |
|---|---:|---:|---|
| `EVAL_TOL` | `1e-12` | `1e-5` | Sharded validation loss at identical weights |
| `STEP_TOL` | `1e-12` | `1e-5` | Loss and gradients of one direct `_run_step` |
| `STEP_PARAM_TOL` | `1e-12` | `1e-4` | Post-AdamW parameters after one direct `_run_step` |
| `TRAJ_TOL` | `1e-10` | `1e-4` | Step losses, validation losses, and `final_trainable` rel L2 over multi-step `fit()` |
| `TRAJ_UPDATE_TOL` | `1e-10` | `1e-3` | `param_update = final - init` rel L2 over multi-step `fit()` |

The `float64` tiers check the distributed logic and are never scaled. The `float32` tiers are calibrated against measured platform round-off: `STEP_PARAM_TOL` splits from `STEP_TOL` because AdamW's $g / (\sqrt{v} + \epsilon)$ amplifies float32 gradient round-off on small-gradient coordinates (up to `3.38e-6` observed on Linux x86_64; one-off margin scan in `docs/VERIFICATION.md` §11), and `TRAJ_UPDATE_TOL["float32"]` is `1e-3` (not `1e-4`) because for LoRA the parameter update is much smaller than the weights and the same AdamW amplification accumulates over steps—on Linux x86_64, pure one-process `fit()` itself varied by up to `1.14e-4` between `1` and `2` intra-op threads on a T15(j) `lora_variate` distillation scenario, and pre-recalibration runs reached `1.94e-4` against the one-process reference (one-off measurements in `docs/VERIFICATION.md` §11; reproducible thread-sensitivity probe `scripts/probes/float32_trajectory_noise.py` in `docs/VERIFICATION.md` §17.3 **[V]**). Environment variable `TIMESTRAL_TEST_F32_TOL_SCALE` (default `1.0`, validated as a finite positive float by `f32_tol_scale()`) multiplies every `float32` tier only (`float64` tiers are unchanged), enabling headroom checks below `1.0` (`0.1` on macOS arm64 for 10× headroom, `0.2` on Linux x86_64 at `1`, `2`, and `4` intra-op threads for 5× headroom; `docs/VERIFICATION.md` §17.1 **[V]**) or loosening above `1.0` when exploring a new platform.

## 12. Open Questions & Risks

- **Target frame (D2).** Confirmed by calibration measurements on synthetic data for 5M and 28M (§4.3). Still not confirmed by Mistral, and not checked on real data, with covariates, or on 123M and 209M.
- **Hyperparameters.** Default `sign_flip=True`, learning rates (`head_only=3e-3`, `lora_variate=3e-3`, `lora_temporal=1e-3`, `full_ft=1e-4`), and LoRA defaults (`r=8, alpha=16, targets=("q","k","v","o")`) are backed by 3-seed validation & forgetting sweeps on `123M` and `209M` plus full-grid sweeps on `5M` and `28M` (`docs/BENCHMARKS.md` §2, `docs/VERIFICATION.md` §14, D19). As a user recommendation (not a default), setting `learning_rate=3e-4` for `full_ft` on `5M` and `28M` gave lower error (three seeds on `5M`, one seed on `28M`, mainly on volatility for `28M`) at the cost of roughly two to three percentage points more forgetting; keep `1e-4` on `123M` and `209M`, where the two rates tie or favour `1e-4` on validation and `1e-4` forgets less (`docs/BENCHMARKS.md` §2.2).
- **Benchmark contamination.** The paper says the models were post-trained on "a mixture of real and synthetic data" and does not list the real datasets. Any public benchmark dataset may have been seen. Results in `docs/BENCHMARKS.md` state this explicitly: the strict realised-volatility test targets (`2026-11-03` to `2026-11-20`) are post-release, while the retail-demand test targets (`2024-06-21` to `2024-07-02`) and the extended 10-month 2026 volatility holdout (`2026-01` to `2026-11-20`) are mostly or wholly pre-release.
- **Upstream drift.** Upstream is a first release with no stability promise. The drift-check job detects changes; re-vendoring requires re-running T1–T3 and T11.
- **Benchmark dataset choice.** Selected and pinned with permissive licences (`twelvedata/financial-world-model` MIT, `Dingdong-Inc/FreshRetailNet-50K` CC BY 4.0, `Salesforce/GiftEval` Apache-2.0; `docs/BENCHMARKS.md`).
- **Float32 gradients through the released weights are not at round-off.** Against a float64 reference, float32 gradients of the training loss with PyTorch's default attention kernel differ by up to 3.4e-3 on CPU, 2.1e-3 on the Apple GPU and 1.1e-2 on CUDA **[V]**, while forward outputs agree to about 3e-7. It depends on the weights, not the architecture: a randomly initialised model is at 4e-7 on every device.
  - *Measured cause* **[V]**. The released checkpoints have large query and key weights (5M layer 5: `||Wq||_2 = 141.6`, `||Wk||_2 = 82.4`; 28M layer 1: `196.1` and `160.6`), which produce attention logits of 370k–404k in 5M and 203k–503k in 28M across the probe layouts. One float32 step at those magnitudes is 0.016 to 0.031.
  - *Effect 1: the fused attention kernel.* At such logits the float32 backward pass of PyTorch's fused scaled-dot-product-attention kernel loses accuracy. On CPU it is the flash kernel: disabling that flag alone takes a 5M error from 1.1e-3 to 1.4e-5. Running attention unfused, either through PyTorch's unfused kernel or written out as matmul and softmax, lowers the error by 50 to 900 times on CUDA and 2.5 to 130 times on CPU across the eight probe layouts. On the Apple GPU the unfused kernel is identical to the default.
  - *Effect 2: near-ties between large logits.* When two keys of one query sit within an $O(1)$ gap at a logit of several hundred thousand, float32 cannot represent the gap accurately in any kernel, and the softmax weights depend on how each kernel rounds. T14's 5M batch with past-only covariates has such a query (two keys 3.46 apart at 351k; a one-off trace, `docs/VERIFICATION.md` §11). On that batch the worst kernel differs by machine: the unfused kernel on an Apple CPU (9.0e-3), explicit attention on an x86 CPU (5.3e-3), the default on CUDA (1.1e-2). A standalone attention call reproduces errors of about 1.5e-2 at logits of 350k–400k under every kernel.
  - *A third, separate source: upstream's RMSNorm* computes in float32 whatever the model's dtype. Left that way in the float64 reference, it moved the reference itself by up to 3.8e-3, so the reference computes RMSNorm in float64, without editing vendored code. RoPE still builds its table in float32, which remains a limit of the reference.
  - *Consequences.* The gradient direction is nearly unaffected: one minus the cosine is at most 5.7e-6 with the default kernel on CPU and the Apple GPU, 5.6e-5 on 5M/28M CUDA, and `2.4e-7` on `123M`/`209M` CUDA (whose peak logits are 3×–4× lower at `123k–132k`, giving default-SDPA CUDA gradient errors of `2.6e-4–6.9e-4`). **`head_only` training is not affected:** head gradients match the reference within 2.8e-6 on all four model sizes. Across 20-step 5M/28M trajectories and 120-step real-data `123M`/`209M` retail training (`docs/VERIFICATION.md` §13–§14, `docs/BENCHMARKS.md` §3), `bf16` with default SDPA matches or beats `fp32` math SDPA (`123M`: `0.1981` vs `0.1978`; `209M`: `0.1947` vs `0.1951`), so the library keeps PyTorch's default kernel (D15).
  - *Evidence.* Acceptance test T14 for the per-scenario maxima, the cosines, the near-tie case and `head_only`; `scripts/probes/gradient_accuracy.py` for the error matrix, the three-way kernel comparison, the standalone attention call, the effect of float32 RMSNorm on the reference, the peak and near-tie logits with weight norms, and the seed sweep; `scripts/cuda_check.sh` for all of these on CUDA; one-off runs for the 351k query trace, the kernel timings, and the float64-weights, TF32 and FP-fusion checks on CUDA (`docs/VERIFICATION.md` §6, §11, §13).
- **Validation loss under `median_folded` is measured in units that move with the model.** From the second horizon patch on, the frame is built from the model's own predicted medians, so two checkpoints are scored against slightly different normalised targets. Early stopping and best-state restoration compare those losses across steps. The effect shrinks with context length (the frame is dominated by the context) and is absent for horizons of one patch. Use `timestral_tune.utils.evaluate_forecaster` (raw-space MASE, wQL, pinball, coverage) for model selection across runs.
- **Apple GPU scope.** Needs PyTorch 2.8 or newer. Verified on one 16 GiB Apple M4 machine (`5M`/`28M` on 2.8.0 and 2.15.0; `123M`, `209M`, and contexts `4,096..32,768` on 2.15.0 only; `docs/VERIFICATION.md` §15).
- **Synthetic replay scope (D7).** Built-in `SyntheticReplaySource` is a simple regulariser, not Mistral's unreleased corpus. In our 5M retail `full_ft` ablation (`docs/BENCHMARKS.md` §5), neither synthetic pinball replay (`+4.1%` at 64 series, `+2.8%` at 256 series) nor synthetic-context distillation (`distill_weight=0.1`: `0.1999`, worst `+1.3%`) beat simply lowering the learning rate to `2e-4` (`0.1995`, worst `+1.3%`); and on `lora_temporal`, `3e-3 + replay_0.25` only recovers the accuracy/forgetting of shipped `1e-3`. Real general-domain replay datasets remain untested.
- **`torch.compile` on PyTorch 2.4.0 with Python older than 3.12.** `compile_model=True` needs `setuptools` installed there: PyTorch's compiler imports it, and that release's Python 3.10 wheel does not declare it **[V]** (`docs/VERIFICATION.md` §10). torch 2.8.0 on Python 3.10 installs it.
- **Worker processes on macOS with PyTorch 2.4.0.** A DataLoader with `num_workers > 0` leaves the process hanging at exit there **[V]**. It is a PyTorch issue that reproduces without this library and is gone by 2.8.0; `num_workers` defaults to 0.
- **CUDA scope.** Verified on one NVIDIA L4 and on one NVIDIA GeForce RTX 3060 (on the 4-GPU host) with PyTorch 2.15.0 (CUDA 13.2), in both `fp32` and `bf16` (including `torch.compile`, power-of-two shape bucketing under `reduce-overhead`, `bf16` dual-orientation head-cache autocast, all four training modes, replay/distillation on both tiny and released `Timestral-5M` plus cached and live-LoRA `reduce-overhead` CUDA graphs, `load_lora` resume, and T1–T14: `580 passed, 4 skipped` on Python 3.12 at `89ac249`, `735 passed, 4 skipped` including the CPU/`gloo` multi-process suite on `uv`-selected Python `3.15.2` at `71514a6` and Python `3.12.16` at `82a21ca`, and `840 passed, 4 skipped` including `tests/test_multi_gpu_check.py` on Python `3.12.16` on L4 at `d474f82` and on one RTX 3060 of the 4-GPU host at `3ac7c6d`; `docs/VERIFICATION.md` §13 **[V]**). There is no CUDA machine in CI. NVLink / GPU P2P multi-GPU setups, T15 on NCCL, older GPUs, and other PyTorch versions are untested (a single 4× RTX 3060 PCIe/SHM separate-GPU session ran at `3ac7c6d`, `docs/VERIFICATION.md` §17.4). On CUDA—and on CPU `torch.compile` tests—recent PyTorch compiles C/C++ helpers that require a C++ compiler and the interpreter's `Python.h` **[V]**; without `Python.h` (for instance on Ubuntu's system Python `3.10` without `python3-dev`), every CUDA forward and every `torch.compile` test fails with a compiler error. A `uv`-managed Python ships the headers.
- **PyTorch `F.linear` `requires_grad` dispatch on non-contiguous inputs (affects one-process `full_ft` distillation at step 0 too) [V].** Measured on CPU across macOS arm64 (PyTorch `2.4.0` and `2.15.0`) and three Linux x86_64 cloud VMs (PyTorch `2.14.1+cu130` and `2.15.0+cu132`; `scripts/probes/linear_requires_grad_dispatch.py`, full per-platform tables in `docs/VERIFICATION.md` §17.2): standalone `F.linear` on permuted non-contiguous inputs differs depending on whether `weight.requires_grad` is `True` or `False`, with `0.00e+00` difference on contiguous inputs and `0.00e+00` between `enable_grad` and `no_grad` for the same flag on every machine tested. On macOS arm64 the standalone difference appears in `float32` only (`0.00e+00` in standalone `float64`); on Linux x86_64 it is **non-zero in standalone `float64` as well as `float32`**, and both the affected shapes and magnitudes vary across x86_64 CPUs even on the same PyTorch wheel (while `2.14.1+cu130` and `2.15.0+cu132` are identical on the AMD EPYC 7B12 VM). On the tiny random model, because `_frozen_base` has `requires_grad=False`, a `full_ft` student and an identical-weight frozen teacher differ at round-off (`0.00e+00` everywhere when the teacher keeps `requires_grad=True`), across 5–6 of 8 cells in `float32` on macOS arm64 (varying between `2.4.0` and `2.15.0`, with `cov bs=4,8` zero) and across 7 of 8 cells (`uni bs=2,4,8` and all `cov bs=1,2,4,8`) in **both** `float32` and `float64` on all three Linux x86_64 VMs. At step 0, `1 / smooth_beta` amplifies `float32` round-off into a non-zero student distillation gradient (order `1e-4` L2 at default `smooth_beta=1e-3`, order `1` at `smooth_beta=0.0`), and because dispatch varies with batch size, one-process cached/live or split batch sizes can disagree at step 0 (motivating T15(j)'s moved-student check in `float32`, §9; in `float64` at `smooth_beta=1e-3`, Linux step-0 `grad_l2` stays `<= 6.19e-13`, so T15's `1e-10` `float64` tier still clears). GPU/CUDA `F.linear` dispatch has not yet been executed on CUDA hardware (`scripts/probes/linear_requires_grad_dispatch.py` accepts `--device cpu|cuda` as of `d4ddf38`). Two candidate remedies exist—leaving `_frozen_base` weights with `requires_grad=True` (still evaluated under `torch.no_grad()` and omitted from the optimiser), or making non-contiguous inputs contiguous before `F.linear`—both of which would change shipped one-process numerics and are therefore left as a decision for the maintainer.

Encountering a shorter trailing-batch shape on one rank can trigger graph recompilation while peers wait inside the next collective; NVLink/P2P behaviour and compilation skew against short explicit `init_process_group(..., timeout=...)` values (D35) remain unmeasured. Separately, across single-L4 sessions S2–S5 (`a20d386`, `866816a`, `8e8f490`, `d474f82`, `docs/VERIFICATION.md` §17.4), the compiled CUDA `float32` rows (`compile_default_lora_variate`, `compile_default_lora_replay`) varied run-to-run against their one-process compiled reference on both tiny and released weights—including across S3, S4, and S5 under the same GPU driver—while graph counts and exact cross-rank equality held every time; the cause of this run-to-run compiled parity variation on CUDA is uninvestigated, and separate-GPU run-to-run variation is unmeasured (S6 ran once).
  - *Per-step costs unmeasured on multi-GPU hardware:* four potential overheads need measurement in Stage 3: (i) Python per-parameter gradient pack/unpack loops in `GradientReducer`, (ii) small collectives per active step (3 without replay: stats `all_reduce`, `GradientReducer.reduce()`, and `on_step_end` `broadcast_status`; 4 with replay adding the 2-element pre-check `all_reduce`), (iii) retaining `GradientReducer`'s flat gradient buffer in accelerator memory through validation inside `fit()` (released only in `cleanup()` after `fit()` ends), and (iv) graph recompilation on shorter trailing-step shapes under `compile_mode="default"`.
  - *`DataLoader` worker teardown skew across ranks* **[V]**: with `num_workers > 0` (`persistent_workers=True`), PyTorch's macOS worker shutdown waits `MP_STATUS_CHECK_INTERVAL` (~5 s) per active worker and differs across ranks when trailing training or validation shards are uneven, so ranks can return from `fit()` seconds apart. Because `strategy.cleanup()` runs after end-of-fit collectives (D30) and the replay loader runs in the main process (`num_workers=0`, D36), this does not stall end-of-fit collectives under default timeouts. In `distributed_trainer_check.py`'s `workers_uneven_f32` row (`num_workers=2`, `docs/VERIFICATION.md` §17.4), `tail_s` stayed sub-second across both single-L4 (`8e8f490`/`d474f82`) and separate-GPU 4× RTX 3060 (`3ac7c6d`) Linux runs against ~20 s on macOS arm64 CPU/`gloo`.
  - *Separate-GPU `torchrun` launch and `LOCAL_RANK` binding exercised on PCIe/SHM only:* `torchrun` on Linux with `device="auto"` → `cuda:LOCAL_RANK` per-rank CUDA binding (`--device-map per-rank`, `cuda:0..1` and `cuda:0..3`, `NCCL_MULTI_RANK_GPU_ENABLE` unset) has now been exercised on 4× NVIDIA GeForce RTX 3060 (`3ac7c6d`, `docs/VERIFICATION.md` §17.4 **[V]**; PCIe/SHM transport observed in one-off session-harness checks), alongside earlier single-L4 shared-GPU runs (`device="cuda:0"`, `8e8f490`, `d474f82`); the other branches of `_resolve_rank_device` remain unit-tested with mocks only, and NVLink / GPU P2P topologies and T15 under `tests/distributed_harness.py` remain unverified in Stage 3.
  - *Learning rates at effective batch `> 32` not swept:* shipped defaults (D19) were swept only at batch sizes 16 and 32 (`docs/BENCHMARKS.md` §2); convergence and forgetting at effective batches 64–128 are unmeasured.
  - *Unpropagated failure paths, NCCL `SIGABRT` behaviour, and user-script cleanup* **[V]**: single-rank `Exception` propagation in `__init__`, `fit()` pre-check domain fetch and local stage (including replay), sharded validation, and rank-0 callbacks is implemented and tested on CPU/`gloo` (T15(d), T15(i), T15(l)), but `BaseException`, `is_oom_error` (forward and backward), device-binding errors, backward failures, post-broadcast `__init__` errors, killed processes, and broken device contexts are not propagated and fall under D35's fail-by-timeout rule. In `scripts/probes/distributed_rank_failure_check.py` across single-L4 (`8e8f490`, `d474f82`) and separate-GPU 4× RTX 3060 (`3ac7c6d`; `docs/VERIFICATION.md` §17.4 **[V]**; PCIe/SHM transport on S6 was a one-off session-harness observation), killing rank 1 mid-`fit()` never hung on any tested platform, but surviving ranks behaved differently by backend and OS: on CPU/`gloo`, survivors raised a Python `RuntimeError` (promptly on TCP transport reset on Linux x86_64, or at the process-group timeout on macOS arm64) and unwound cleanly; on CUDA/NCCL (both on one shared L4 and on 2 or 4 separate RTX 3060 GPUs), survivors were killed by `SIGABRT` after the process-group timeout plus NCCL's health-check wait with no Python exception raised, so `except`/`finally` blocks inside `fit()` and user scripts (including `finally: dist.destroy_process_group()` in §7.6) did not run. NVLink / GPU P2P NCCL rank-failure behaviour is still unmeasured, and what cleanup guidance or process-group handling (if any) user scripts should expect on NCCL peer death remains an open question.
  - *Concurrent Hub downloads across ranks not exercised live:* public `load_model()` takes no rank-0 download barrier and relies on `huggingface_hub`'s per-file `WeakFileLock` (D29). Source inspection confirms `snapshot_download` delegates to `hf_hub_download` with `WeakFileLock` in both installed `2.4.0` and the `0.23.0` floor (`docs/VERIFICATION.md` §12), but concurrent multi-process downloads have not been run live on either version.
  - *Accelerator memory on every rank (`full_ft` `_frozen_base` and flat gradient buffer, arithmetic):* allocating one flat reduction buffer alongside `p.grad` during `fit()` doubles accelerator gradient memory for the trainable set. In addition, `full_ft` with distillation (`distill_weight > 0`) skips teacher output caching in multi-process mode (D32) and holds one live frozen copy of the entire model (`_frozen_base`) on every rank's device alongside the trainable model. As arithmetic on `Timestral-209M`'s `209,312,256` parameters (§3.1, `docs/BENCHMARKS.md` §3), `full_ft` in `fp32` (`4 B/param`) adds `~798 MiB` (`~0.78 GiB`) per rank for the flat gradient buffer and another `~798 MiB` per rank for `_frozen_base` when distilling (not measured); chunked/bucketed reduction (or a DDP wrapper, D22) is the mitigation to evaluate if VRAM becomes tight.
  - *Host memory scales with `N`:* each rank is a separate OS process holding its own copy of `train_dataset` / `val_dataset` / `replay_dataset` and its own `DataLoader` worker processes (`num_workers > 0`, up to two persistent pools per rank; D36).
  - *`export()` read race:* because `export()` is collective-free (D31), returning on a non-zero rank does not guarantee rank 0 has finished writing files; multi-process scripts reading the export from non-zero ranks must synchronise explicitly (e.g. `dist.barrier()`).
  - *API and runtime ergonomics observations from the Stage 3 driver (first outside consumer; suggestions for maintainer decision, not decisions):*
    1. *`TrainingConfig.device` typing (`src/timestral_tune/config.py:312`):* annotated `str = "auto"`, while `DistributedContext.detect()` (`src/timestral_tune/trainer/distributed.py:271`) and `resolve_device()` (`src/timestral_tune/models/loader.py:42`) accept `str | torch.device | None` (on `"nccl"`, `"auto"`, `"cuda"`, unindexed `torch.device("cuda")`, and `None` all select `cuda:LOCAL_RANK`). Passing `None` to `TrainingConfig(device=None)` requires `# type: ignore`, and `export.py` serialises `config.device` directly to JSON (which would fail on a `torch.device` object).
    2. *No one-process opt-out inside an active process group (`src/timestral_tune/trainer/trainer.py:356-368`):* `TimestralTrainer.__init__` always enters multi-process mode when `dist.is_initialized()` and `world_size > 1`, so a script launched under `torchrun` cannot run a rank-0-only one-process `TimestralTrainer` (e.g. for local reference or calibration) without first destroying the process group.
    3. *`export()` logging for in-memory models and non-zero ranks (`src/timestral_tune/export.py:168-173`, `src/timestral_tune/trainer/trainer.py:1618-1636`):* exporting an in-memory model emits a `logger.warning` about the missing base `LICENSE` on rank 0 (and in one-process runs; reaching `stderr` via Python's `lastResort` handler when logging is unconfigured), while non-zero ranks emit a `logger.info` skip notice and return before rank 0 finishes writing (see also *`export()` read race* above).
    4. *`compile_mode="default"` graph count with replay (`docs/VERIFICATION.md` §17.4 **[V]**):* across every multi-rank driver run, `compile_default_lora_replay` compiled more Dynamo graphs (`5` total) than `compile_default_lora_variate` without replay (`2`) and more than the cached one-process reference (`2`–`3`, which skips live `disable_lora` teacher forwards). Whether toggling `disable_lora`/`eval()`/`no_grad()` across distinct domain and replay layouts causes noticeable compile overhead on larger models is unmeasured.
- **Pre-existing one-process observations (predating Phase 5; unchanged, left for maintainer decision) [D]:**
  1. *Cached teacher quantiles cast to `float32`* **[D trainer/trainer.py:TimestralTrainer._precompute_replay_base_outputs]**: cached teacher quantiles are always stored as `torch.float32` regardless of model dtype, so a `float64` model with `cache_base_outputs=True` distils against `float32`-truncated targets.
  2. *Direct `training_step()` in cached `full_ft` distillation* **[D trainer/trainer.py:TimestralTrainer.training_step, _setup_replay_teacher, _compute_replay_terms_with_counts]**: when `cache_base_outputs=True` builds the CPU cache in `full_ft`, `_frozen_base` stays `None`; calling `training_step(batch, replay_batch=...)` directly without `replay_teacher_quantiles` falls into the `disable_lora(self.model)` branch, where `disable_lora` is a no-op without adapters, distilling the student against itself.
  3. *Cache builders advance global PyTorch RNG* **[D trainer/trainer.py:TimestralTrainer._build_head_cache, _raw_loader, _precompute_replay_base_outputs]**: both cache builders iterate a `DataLoader` with `generator=None`, drawing from PyTorch's global RNG; because `_build_head_cache` runs lazily during the first `fit()` after `torch.manual_seed(config.seed)` and is reused on subsequent `fit()` calls, a first `fit()` and a later one see different global RNG states.
  4. *`SyntheticReplaySource` `missing_rate > 0` endpoint-only guard* **[D replay/generators.py:SyntheticReplaySource.__init__]**: the docstring promises at least one observed step in every window's context and horizon, but the code only protects the first and last steps of the whole series (`drop[0] = False`, `drop[-1] = False`).
  5. *Cached vs live teacher batch size* **[D trainer/trainer.py:TimestralTrainer._precompute_replay_base_outputs, _replay_loader, _compute_replay_terms_with_counts]**: the cached teacher pass runs at `eval_batch_size or batch_size`, whereas the live teacher pass runs at `ReplayConfig.resolved_batch_size(batch_size)`.
  6. *Stopping in `on_fit_start` still runs final validation* **[D trainer/trainer.py:TimestralTrainer._run_fit_loop]**: because `last_evaluated_step` initialises to `-1` while `global_step` starts at `0` (or `start_step`), setting `trainer.should_stop = True` in `on_fit_start` skips training steps and still triggers the post-loop final `evaluate_now()` when `val_dataset` is set.
  7. *Skipped batches extend `epochs`-bounded runs* **[D trainer/trainer.py:TimestralTrainer._init_runtime, _run_fit_loop]**: `total_steps` is set to `epochs * epoch_steps` and the loop stops on `global_step >= final_step`, so skipped zero-scored batches can push an `epochs`-bounded run into an extra epoch.
  8. *`evaluate()` re-validates on every call* **[D trainer/trainer.py:TimestralTrainer.evaluate]**: runs `_check_dataset(dataset, "dataset")` on every call (including for `self.val_dataset`, already validated in `__init__`).
  9. *`ProgressLogger` mixes per-fit and global step counts* **[D trainer/callbacks.py:ProgressLogger.on_step_end, on_evaluate, on_fit_end]**: `on_step_end` logs per-fit step count (`step - fit_start_step` out of `total_steps`), `on_evaluate` logs global `step`, and `on_fit_end` logs per-fit `result.steps` alongside global `result.best_step`.
  10. *`export_checkpoint` ignores `lora_config` on non-LoRA models* **[D export.py:_validate_export_inputs, export_checkpoint]**: when `has_lora(model)` is `False`, a passed `lora_config` is silently ignored (`effective_lora = None`) rather than rejected.
  11. *macOS `TMPDIR` length silently deadlocks `DataLoader` workers (`num_workers > 0`)* **[D trainer/trainer.py:TimestralTrainer._build_data_loader]**: on macOS, PyTorch `DataLoader` workers share tensors through `torch_shm_manager`, which binds an `AF_UNIX` socket under `TMPDIR`. When that socket path exceeds macOS's 103-byte `sun_path` limit (a `TMPDIR` of roughly 70 bytes is enough), the worker's feeder thread raises, drops the batch, and stays alive, so the main process waits forever at 0% CPU with no error. Reproduced without project code; affects one-process `TimestralTrainer.fit()` with `num_workers > 0` the same way as multi-process `fit()`, and the library has no guard (`docs/DEVELOPMENT.md`). *Candidate remedy (for maintainer decision):* fail fast in `_build_data_loader` when `num_workers > 0`, `torch.multiprocessing.get_sharing_strategy() == "file_system"`, and the expected socket path under `tempfile.gettempdir()` would exceed the platform limit, instructing the caller to set a shorter `TMPDIR` (e.g. `TMPDIR=/tmp`).
  12. *`load_model(..., dtype=torch.float64)` truncates weights through `float32`* **[D models/loader.py:load_model]**: `load_model` instantiates `TuneTimestralModel(config)` in default `float32`, calls `model.load_state_dict(...)` into those `float32` parameters (silently truncating `float64` weights in `model.safetensors` to `float32`), and only afterwards casts via `model.to(device=target, dtype=dtype)`. As a result, a `float64` export cannot be reloaded to better than `float32` precision (motivating the `1e-6` float64 export-reload tolerance in `scripts/probes/distributed_trainer_check.py`; one-off `tiny_random` measurements without a tracked probe in `docs/VERIFICATION.md` §11). Recorded and left unchanged for maintainer decision. *Suggested remedy (suggestion only):* cast the model to `dtype` before calling `load_state_dict` (e.g. `model.to(dtype=dtype)` before `load_state_dict`, then `model.to(device=target)` and `rebuild_inv_freq()`), which restored float64 round-off agreement in the §11 one-off check.
